# FlowPanel 0.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 0.3.0 — the release after which a real Next 16 project installs FlowPanel in one command, builds a founder-grade admin (entity cards, analytics dashboards, related histories) from configuration alone, and an agent can read the whole DSL without guessing.

**Architecture:** Every gap comes from one real host (freelance-radar, friction log F1–F43) and from the "10/10" definition in `2026-09-08-10-of-10-from-freelance-radar.md`. Tier 1 (install) closed in 0.2.x work already on this branch. This plan closes Tier 2 (dashboards and detail pages as config), Tier 3 (realtime, SQL, auth presets), Tier 4 (legibility: contract tests, `llms.txt`, did-you-mean, `@flowpanel/test`), then prepares the release. Widgets are one model rendered in two hosts (dashboards and detail tabs); every new primitive is a core type + builder, a `@flowpanel/react` component ≤ 80 LOC, and a `renderWidget` case.

**Tech Stack:** pnpm + turbo monorepo, TypeScript 5.9, Next 16.3 App Router, React 19, Biome, Vitest (+ happy-dom), Playwright, changesets, ts-morph (docs checks).

**Spec:** `docs/spec/2026-09-08-10-of-10-from-freelance-radar.md` (binding), `docs/spec/2026-09-08-friction-log-freelance-radar.md`, memory `flowpanel-0.2-friction-freelance-radar` (F1–F43), `docs/spec/2026-09-08-page-projection-safety.md` (projection rules win over convenience).

## Global Constraints

- One commit per task, message in the repo's imperative style, **no `Co-Authored-By` / "Generated with" trailers**, **≤ 2 commits per calendar day** (squash a third task into the day's second commit before the day ends).
- No `npm publish`, no `git push`, no production DB changes. The user pushes.
- Code without comments (1–2 lines max where a line would otherwise mislead). Rationale lives in changesets and ADRs.
- Configs decompose by resource / dashboard; no monolithic files. `scripts/check-file-sizes.ts` threshold is 300 LOC.
- English in every repo artifact. Every label a reader can see comes from `LabelsConfig` with an English default and a `RU_LABELS` entry.
- Public API changes: JSDoc with `@defaultValue` where a default exists, an `api-ownership` rule in `scripts/docs/api-ownership.ts`, a reference page section, a changeset.
- Projection rules (`page-projection-safety.md`) are not relaxed for convenience: a `render(row)` callback still receives the declared/exposed fields.
- Row identity rule: scalar string/number/bigint only; keyless rows render but never act.
- Compatibility matrix unchanged: Node ≥ 20, Next ^16.3, React/DOM ^19 identical exact version, Drizzle ≥ 0.45.2 < 1 or Prisma ≥ 5 < 7.
- Run gates one suite at a time (react + next in parallel saturate the machine). Gate list per task: `pnpm --filter <pkg> test:unit`, `pnpm typecheck`, `pnpm lint`, `pnpm test:types`, `pnpm build`, `pnpm check:docs`, `pnpm check:release`, `pnpm check:cycles`, `pnpm check:changesets`.
- Every task ends with an independent review (task reviewer) before the next task starts.
- Do not touch `packages/core/src/types/context.ts` `QueryContext.db` removal: it stays in 0.3 (ruling below).

## Rulings recorded before execution

1. `QueryContext.db` says "Removal target: 0.3". It stays; the JSDoc moves the target to 1.0. Removing it breaks every dashboard query in the two known hosts while `ctx.sql` is still new. Cost if wrong: one more minor carries a deprecated field.
2. `DetailTab.render(row, ctx)`: `row` stays projected (spec `page-projection-safety.md` is binding); the second `ctx` argument is new. Cost if wrong: hosts keep declaring `detail.expose`.
3. `ctx.series()` is not an adapter method. Bucketing is dialect-specific SQL; `ctx.sql` + `fillDays()` cover the need with two honest primitives. Cost if wrong: a host writes one `date_trunc` line per series.
4. The founder-shaped example is the existing `examples/ai-scraper` Overview and Customers entity card rebuilt on the new widgets, not a new example app. It is already the e2e/a11y fixture, so it dogfoods everything. Cost if wrong: one example instead of two.
5. `@flowpanel/test` ships as a twelfth package with one export, `smokeAdmin`. It joins the fixed changeset group and every release gate.
6. `rowClick` default becomes `"detail"` when `detail` is configured and no `drawer` is; an explicit value always wins. `pieChart.showLegend` default flips to `true`. Both are documented as behaviour changes in the upgrade guide.
7. Package versions on `main` are 0.1.0 while npm has 0.2.0 (the version PR was merged, then main was rewritten). Task 9 reproduces the 0.2.0 bump locally from the eleven 0.2 notes so the next version PR yields 0.3.0.

```ts
// @flowpanel/core/publish  (re-exported by @flowpanel/kit/publish)
export interface RedisLike { publish(channel: string, message: string): Promise<number>; on(event: "error", cb: (err: unknown) => void): unknown; duplicate?(): RedisLike & { subscribe(c: string): Promise<number>; unsubscribe(c: string): Promise<number>; on(event: "message", cb: (c: string, raw: string) => void): unknown } }

export function createPublisher(opts: { redis: RedisLike | string; keyPrefix?: string }): PublisherClient

export type PublisherOptions = { driver: "memory" } | { driver: "redis"; url?: string; client?: RedisLike; keyPrefix?: string };
```

**Behaviour:**
- Publish-only usage opens one connection (or uses the host's client); the subscriber connection is created lazily on the first `subscribe`, via `duplicate()` when a client was given, else a second `new Redis(url)`. Every connection gets `.on("error", …)` that logs once per error kind and never throws (F23).
- The wire envelope (`{channel, payload}` per ADR 0014) is owned by `envelope.ts`; workers import `@flowpanel/kit/publish` and nothing else (F36). `next/publish.ts` uses the same functions.
- `bindPublisher(config)` rebinds when `config.realtime` differs from the bound options (JSON-stable compare) or when `config` is a different object in development (HMR); the previous publisher is closed.
