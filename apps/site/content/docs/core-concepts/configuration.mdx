The flowpanel config is a single `defineAdmin({...})` call that returns
a `ResolvedAdminConfig`. Everything the admin renders, every behavior
it allows, every connection it makes — all of it lives here.

## Shape

```ts
import { defineAdmin, resource } from "@flowpanel/kit";
import { drizzleAdapter } from "@flowpanel/kit/drizzle";
import { db } from "@/server/lib/db";
import * as schema from "@/server/lib/db/schema";
import { getSession } from "@/server/lib/auth";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof db;
  }
}

export default defineAdmin({
  adapter: drizzleAdapter({ db, schema }),
  auth: {
    session: getSession,
    role: (s) => (s as { user?: { role?: string } } | null)?.user?.role ?? "guest",
    requireRole: "admin",
  },
  resources: [
    resource(schema.users, { columns: ["email", "role"] }),
  ],
});
```

## Top-level options

| Option | Type | Description |
|---|---|---|
| `adapter` | `Adapter` | Data source plug-in. `drizzleAdapter`, `prismaAdapter`, or your own. |
| `auth` | `AuthConfig` | Session loader + role function (required). |
| `resources` | `ResourceConfig[]?` | The list of CRUD surfaces to expose. |
| `dashboards` | `DashboardConfig[]?` | Custom dashboard pages at `/admin/<path>`. |
| `pages` | `PageConfig[]?` | Your own React components (or external links) rendered inside the admin shell. |
| `queues` | `QueueConfig[]?` | BullMQ queues to surface in the admin nav. |
| `theme` | `ThemeConfig?` | Brand, accent, CSS vars, and `theme.components` slot overrides. |
| `shell` | `ShellConfig \| ShellMode?` | `"sidebar"` (default), `"tabs"`, or `"bare"`. |
| `labels` | `LabelsConfig?` | i18n strings for the built-in chrome. |
| `realtime` | `RealtimeConfig?` | `{ driver: "memory" }` for dev, Redis for prod. |
| `audit` | `AuditConfig?` | Mutation audit log sink + retention. Nothing is recorded until you set `sink`. |
| `rateLimit` | `RateLimitConfig?` | Per-user or per-IP throttling. |
| `security` | `SecurityConfig?` | Default-on same-origin protection for write routes, plus explicitly trusted origins. |
| `readOnly` | `boolean?` | Put the whole admin in read-only mode — disables every write form, drops actions, blocks mutations server-side. Great for a public demo or viewer role. |
| `basePath` | `string?` | URL prefix the admin's **pages** mount under. Defaults to `/admin`. A missing leading `/` is added and a trailing one stripped, so `"internal/admin/"` and `"/internal/admin"` are the same. |
| `commandPalette` | `CommandPaletteConfig?` | Extra `⌘K` entries. |
| `scope` | `(ctx) => Scope?` | Multi-tenant query scoping. |
| `hooks` | `{ onError? }?` | Request lifecycle hooks. |

By default the admin's pages mount at `/admin`. Set `basePath` to relocate
them — nav links, redirects and `revalidatePath` calls all flow through
`buildHref`, so `basePath: "/internal/admin"` works once you move the page
file to `app/internal/admin/[[...slug]]/page.tsx`.

<Callout type="warn">
`basePath` moves the **pages only**. Leave the API routes exactly where
`init` put them — `app/api/flowpanel/[...route]/route.ts` and
`app/api/flowpanel/stream/route.ts`. The browser-side callers build their
URLs from a hardcoded `/api/flowpanel` prefix (drawer fetch, inline edit,
import, restore, reference search, and every row / bulk / dashboard
action), so moving the API route breaks all of them with 404s while the
pages still render.
</Callout>

Full type signatures live on the **Reference / defineAdmin** page.

## Cross-origin write protection

FlowPanel rejects cross-origin mutations by default. The Next.js runtime checks
the browser's `Origin` and Fetch Metadata headers before it loads the session or
runs an action. Same-origin requests and trusted server-to-server clients that
do not send browser headers continue to work.

If a separate operations frontend must submit writes, allow its exact origin:

```ts
defineAdmin({
  // ...
  security: {
    trustedOrigins: ["https://ops.example.com"],
  },
});
```

Behind a proxy, add the public origin when the request URL visible to Next.js
uses an internal host. `sameOrigin: false` is available only for deployments
whose gateway enforces an equivalent CSRF policy; disabling both protections
is unsafe for cookie-authenticated admins.

## One resource per file

The single-file config above is the shape `flowpanel init` writes and the
shape every sample on this site uses, because a sample has to fit on screen.
It is not the shape a real admin should keep: `resource()` returns a plain
`ResourceConfig`, so a config of any size decomposes into one file per
resource with no framework support required.

```text
src/admin/
├── resources/
│   ├── users.ts
│   ├── orders.tsx        # .tsx — this one has a render column
│   └── invoices.ts
├── dashboards/
│   └── overview.ts
└── config.ts             # or keep flowpanel.config.ts at the root
```

Each file exports one builder call:

```ts title="src/admin/resources/users.ts"
import { resource } from "@flowpanel/kit";
import * as schema from "@/server/lib/db/schema";

export const users = resource(schema.users, {
  columns: ["email", "role", "createdAt"],
  search: ["email"],
  defaultSort: { field: "createdAt", dir: "desc" },
});
```

```tsx title="src/admin/resources/orders.tsx"
import { resource } from "@flowpanel/kit";
import * as schema from "@/server/lib/db/schema";
import { OrderStatus } from "../OrderStatus";

export const orders = resource(schema.orders, {
  columns: [
    "id",
    { field: "status", render: (row) => <OrderStatus status={row.status} /> },
    { field: "totalCents", format: { kind: "money", scale: 100 } },
  ],
});
```

The config file then reads as a manifest:

```ts title="flowpanel.config.ts"
import { defineAdmin } from "@flowpanel/kit";
import { drizzleAdapter } from "@flowpanel/kit/drizzle";
import { db } from "@/server/lib/db";
import * as schema from "@/server/lib/db/schema";
import { getSession } from "@/server/lib/auth";
import { overview } from "@/admin/dashboards/overview";
import { invoices } from "@/admin/resources/invoices";
import { orders } from "@/admin/resources/orders";
import { users } from "@/admin/resources/users";

export default defineAdmin({
  adapter: drizzleAdapter({ db, schema }),
  auth: {
    session: getSession,
    role: (s) => (s as { user?: { role?: string } } | null)?.user?.role ?? "guest",
    requireRole: "admin",
  },
  dashboards: [overview],
  resources: [users, orders, invoices],
});
```

Three things worth knowing:

- **A resource with a JSX `render` belongs in a `.tsx` file.** `flowpanel.config.ts`
  can be renamed `flowpanel.config.tsx` — the CLI looks for both — but moving
  the JSX out to its own module keeps the manifest plain TypeScript.
- **`defineAdmin` is pure**, so importing a resource module has no side
  effects and the config can be imported from a script or a test.
- **Keep the module-augmentation block in one place** (the config file, or a
  dedicated `flowpanel.d.ts`). `declare module "@flowpanel/kit"` merges
  globally, so repeating it per resource file only invites conflicting
  entries.

`flowpanel new <resource>` appends to whichever `resources` array it finds in
the config, so it fits the single-file layout; in a decomposed one, write the
file yourself and add the import.

## Typing your `ctx.db`

Augment `FlowpanelTypes["db"]` once with `typeof db` and both request contexts
that default to it carry the typed client automatically — no per-callsite
annotations. That is `WidgetContext` (every widget `query`, stat resolver and
`custom()` props resolver) and `ActionContext` (every row / bulk / dashboard /
drawer action `run`), plus the adapter's own `db`.

The adapter-facing `QueryContext` family defaults its client to `unknown`
instead, so a `FieldDef.options` or `defaultValue` resolver still narrows
`ctx.db` itself. See [Type registry](/docs/reference/registry#inferdb).

```ts
declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof db;
  }
}
```

Prisma users can also augment `FlowpanelResources` to recover row
inference for `resource("User", ...)`:

```ts
import type { User, Post } from "@prisma/client";
import { prisma } from "@/lib/prisma";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof prisma;
  }
  interface FlowpanelResources {
    User: User;
    Post: Post;
  }
}
```

## Typing cross-resource references

Augment `FlowpanelResources` with each resource name → row type, and every
cross-resource string is checked at compile time — `ColumnDef.reference`
(`resource` **and** `labelField`), drawer / detail-tab `resource`, and widget
`resource`. A typo errors with a "Did you mean?" suggestion.

```ts
declare module "@flowpanel/kit" {
  interface FlowpanelResources {
    users: typeof schema.users.$inferSelect;
    posts: typeof schema.posts.$inferSelect;
  }
}

// elsewhere — checked against the registry:
{ field: "userId", reference: { resource: "users", labelField: "email" } }
```

It's opt-in: leave `FlowpanelResources` empty and those fields stay plain
`string`, so nothing breaks for apps that don't augment it.

## Reload behavior

In development, edits to `flowpanel.config.ts` hot-reload like any
other TypeScript module. In production, the config is bundled into the
route handler at build time — no runtime config parsing.
