---
title: Realtime in production (multi-instance)
description: SSE realtime works out of the box on a single Next.js instance. Multi-instance deployments (Coolify, Vercel, Fly, anywhere with >1 replica) need a Redis-backed publisher.
---

flowpanel ships **two SSE drivers** out of the box:

- **memory** (default) — events live in the running Node process. Perfect for
  `next dev`, single-instance previews, single-container deployments.
- **redis** — events fan out via Redis pub/sub. Required the moment you scale
  past one Next.js instance.

## When you need Redis

The browser opens an `EventSource` connection to **one** instance. If a
mutation lands on a different instance, the in-memory `publishResource()`
fires on the wrong process and the subscribed browser never hears about it.

**Symptoms:** Realtime works locally but not in production. Lists don't
refresh after a peer's edit. The dashboard's "Orders scraped today"
counter doesn't tick up.

You need Redis any time **all** of these are true:

- More than one Next.js instance answers requests for the same admin
  (Coolify with replicas > 1, Vercel with multiple regions, Fly with
  multi-region, Render with autoscale, etc.).
- Sticky sessions are not configured (sticky sessions partially work
  around the issue but break under instance restarts).
- Users have the admin open in browsers and you want their lists to
  update when a peer writes.

If you're just running `next start` on one box, the memory driver is fine.

## Switch on Redis

```ts
// flowpanel.config.ts
import { defineAdmin } from "@flowpanel/kit";

export default defineAdmin({
  // …adapter, auth, resources…
  realtime: {
    driver: "redis",
    url: process.env.REDIS_URL!,
    // Optional: prefix every channel so multiple admins on the same Redis
    // instance don't collide. Defaults to "flowpanel".
    keyPrefix: "fp",
  },
});
```

That switch covers every process that goes through `Flowpanel(config)` or
`handlers(config)` — both call `bindPublisher(config)` for you, so every
existing `resource.realtime: true`, `table({ realtime: "resource.orders" })`
and `publishResource(name, …)` inside a request fans out via Redis instead of
an in-process EventEmitter. (A resource's `realtime` is `boolean | string`;
a widget's is `string | string[]` — a widget names the channels it listens
to, so `true` is not a value it accepts.)

A process that never renders the admin or serves its API — a worker, a cron, a
one-off script — has never seen the config, so it has no publisher bound. Bind
it once at startup:

```ts
import { bindPublisher, publishResource } from "@flowpanel/kit/next";
import config from "@/flowpanel.config";

bindPublisher(config);

await publishResource("orders", { action: "update", id: orderId });
```

Skip that and the publish falls back to an in-memory publisher, logs one
warning, and reaches nobody.

`@flowpanel/kit/server` re-exports the same `publish`, `publishResource` and
`bindPublisher` bound to the same process-wide store, so importing from either
subpath in the same process is equivalent — a `publish` sent through
`/server` reaches a subscriber registered through `/next`.

## What flows over Redis

flowpanel never publishes row contents over Redis. Channels carry just
**resource name + action** — the payload for a resource mutation is
`{ action: "create" | "update" | "delete", id? }`.

The Redis message body is that payload **bare**, `JSON.stringify`-ed and
nothing else. The routing information lives in the Redis channel name, so
there is no envelope to add:

```
flowpanel:resource.orders → {"action":"update","id":"ord_…"}
flowpanel:resource.users  → {"action":"create","id":"usr_…"}
flowpanel:scraper:tick    → <arbitrary payload via publish("scraper:tick", …)>
```

A `publish(channel)` with no payload sends an **empty string**, which the
subscriber reads back as `undefined`.

The `{channel, payload}` envelope is added one layer later, when the SSE
route serializes an event for the browser (ADR 0014 scopes it to the SSE
frame). One EventSource multiplexes many channels, so the frame has to say
which one it belongs to; a Redis subscription already knows.

<Callout type="warn">
If you write an external publisher — a Python worker, a Go service, a
`redis-cli PUBLISH` — send the **bare payload**. Wrapping it in
`{channel, payload}` yourself double-wraps it: the browser then receives
`{"channel":"resource.orders","payload":{"channel":"resource.orders","payload":{…}}}`
and every consumer reading `payload.action` sees `undefined`.
</Callout>

The logical channel name — `resource.<name>` for resource mutations
(automatic; see below), or whatever string you pass to `publish(channel, …)`
for a custom event — is what `<DataTable realtime="...">` and `subscribe()`
callers use. `keyPrefix` only namespaces the string actually sent over the
Redis wire; it never changes the name application code sees. With
`keyPrefix: "fp"` the three lines above become `fp:resource.orders`,
`fp:resource.users`, `fp:scraper:tick` — same logical channels, different
wire prefix.

Browsers subscribed to a list get the channel ping, then
`router.refresh()` re-fetches the (RSC-streamed) updated rows over
HTTPS — Redis is the **notify**, not the source of truth.

## Operational checklist

- **Bind the publisher in workers.** The publisher is already a process-wide
  singleton inside the Next.js server — `Flowpanel` and `handlers` bind it.
  Any process that runs neither (worker, cron, seed script) has to call
  `bindPublisher(config)` itself, or its publishes stay in-process.
- **Install `ioredis`.** It is an optional peer dependency, so a kit install
  does not pull it in. `createPublisher({ driver: "redis", … })` throws
  `ioredis is not installed` on the first publish without it.
- **TLS.** Production Redis providers (Upstash, AWS ElastiCache, Render)
  use TLS. `PublisherOptions` is `{ driver, url, keyPrefix? }` and nothing
  else — there is no place to pass ioredis options such as `tls`. Encode TLS
  in the URL instead: `rediss://…`.
- **HEAD requests / health checks.** SSE responses are long-lived;
  ALBs default to 60s idle timeout. Bump the proxy/LB idle timeout to
  at least 5 minutes, or accept that browsers auto-reconnect every
  minute (works but spammy in logs).
- **Restart hygiene.** Each Next.js instance opens one Redis subscriber
  connection. When you redeploy, in-flight EventSources disconnect and
  reconnect automatically — no data loss, but expect a thundering herd
  of reconnects right after rollout. Stagger your rolling deploy if you
  see Redis CPU spikes.

## Troubleshooting

**Symptom: Browser opens SSE, server sends events, browser receives nothing.**

The proxy/CDN is buffering. SSE needs the response body to stream as
each event lands; common breakage:

- nginx: set `proxy_buffering off;` for the `/api/flowpanel/stream` location.
- Cloudflare: enable "Streaming responses" or disable proxying on the
  stream route via a Page Rule.
- Serverless platforms cap function duration, and an SSE response is a
  long-lived one. The stream route `flowpanel init` scaffolds already
  declares what it needs — `export const runtime = "nodejs"` and
  `export const dynamic = "force-dynamic"` — so keep both if you rewrite it.
  Beyond that, check your platform's current max duration for the plan you
  are on; where it is too short, host the stream route on a long-lived
  server instead.

**Symptom: Browser receives events on instance A but not after a
deploy that lands on instance B.**

Almost always a publisher misconfiguration. The mutation route on
instance A is fanning out in-memory only because either:

1. `realtime` is unset (or `{ driver: "memory" }`) in `defineAdmin` — it
   defaults to the in-memory driver, which can't cross instances, OR
2. `realtime.url` points at a Redis that instance B can't reach, OR
3. `REDIS_URL` env was set on A but not on B during a partial rollout.

`flowpanel doctor` won't catch these — it checks your deps, config, and
the wiring files, not the runtime `realtime` settings. Confirm the
driver and that `REDIS_URL` is set on every instance yourself; a CI gate
on env parity is the only reliable guard against case 3.

resource, installing `ioredis`, publishing your own events — see
