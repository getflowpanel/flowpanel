The adapter is the only part of FlowPanel that queries your database. Implement
this interface for a data layer without a shipped adapter. Overview:
[Adapters and introspection](/docs/understand/adapters).

Shipped adapters: [`drizzleAdapter`](/docs/introduction/drizzle) and
[`prismaAdapter`](/docs/introduction/prisma).

## Adapter

<AutoTypeTable path="../../packages/core/src/types/adapter.ts" name="Adapter" />

`Ref` is what `resource(ref, …)` accepts; `DB` is the client widgets receive as `ctx.db`.
`kind` is a label (`"drizzle"`, `"prisma"` or your own); nothing branches on it.

`kind`, `db`, `introspect`, `inferSchema`, `list`, `get`, `create`, `update` and
`delete` are required. Without `restore`, the restore button is hidden. `sql` and
`count` back [`ctx.sql` and `ctx.count`](/docs/reference/contexts#raw-sql-and-counts).
`applyMigration(id, sql)` and `listAppliedMigrations` power `flowpanel migrate`.

`applyMigration` must serialize migrators at the database and recheck the ID under
the lock, so a concurrent duplicate is a no-op. The shipped adapters run each file
and its marker in one transaction on PostgreSQL and SQLite. On MySQL, which commits
DDL implicitly, Drizzle holds a `GET_LOCK` advisory lock and Prisma a claim row in
`_flowpanel_migration_claims` that records where a failed run stopped; later runs
stop until you repair the schema and delete that row. Both reject procedural
scripts (trigger bodies, stored procedures, `DELIMITER`) unless the body uses
PostgreSQL dollar quoting.

## Audit log

`auditLog` is the `flowpanel_audit_log` table that `0001_init.sql` creates. The
admin appends each [audit event](/docs/guides/audit-log) to it and reads the record
History tabs and the Audit log page from it. The shipped adapters bind every value
through the same client `flowpanel migrate` uses. `list` returns events newest
first; with `scope` set, only those whose stored tenant key equals `scope.key`.
`append` writes one row per id in `targetIds`. Without `auditLog`, an admin with
`audit` on needs a `sink`.

## Raw SQL

`sql` is a tagged template: every interpolated value must reach the database as a
bound parameter, never concatenated.

`count(ref, where)` takes the `list` filter shape. FlowPanel calls it only for
unscoped resources and counts scoped ones through `list`. Both run on the
adapter's own `db`, outside any transaction or per-request session settings.

Two helpers match the shipped adapters' behaviour:

```ts
import { parseSqlRows, sanitizeSqlParams } from "@flowpanel/kit";

async function sql<Row>(strings: TemplateStringsArray, ...values: unknown[]) {
  const rows = await driver.query(strings, sanitizeSqlParams(values));
  return parseSqlRows<Row>(rows);
}
```

`sanitizeSqlParams` binds a `Date` as ISO-8601 text and a `bigint` as decimal text,
as the Drizzle adapter does; the Prisma adapter hands both to `$queryRaw` as they are,
so Prisma binds a timestamp and a bigint.
`parseSqlRows` reads zoneless `YYYY-MM-DD HH:mm:ss` strings as UTC `Date`s, unless
`{ parseDates: false }`.

Arrays differ: Drizzle expands `${ids}` into a list, so `where id in (${ids})`
works; Prisma binds one parameter, so write `where id = any(${ids})` or use
`Prisma.join`.

## ColumnMeta

<AutoTypeTable path="../../packages/core/src/types/adapter.ts" name="ColumnMeta" />

`type` and `enumValues` drive a fully generated form (no `create.fields` or
`update.fields`) and editable list cells:

| Column | Generated form control | Editable cell |
| --- | --- | --- |
| has `enumValues` | `select` | text |
| `number` | `number` | `number` |
| `boolean` | `checkbox` | text |
| `date` | `datetime-local` | `datetime-local` |
| `json` | `json` | text |
| anything else | `text` | text |

Filters and declared fields do not infer a type from the column. `references` is
reported for your own use.

## What an implementation must honor

Three obligations keep the admin safe:

**Tenant scope.** When `ctx.boundScope` is set, every method must constrain
its query with `ctx.boundScope.apply`, and refuse a query the predicate leaves unconstrained. `create` and `update` included: writing or moving a row outside the
caller's scope is as much a leak as reading one.

**The search allowlist.** `list` searches only `ctx.searchFields`.

**Soft delete.** When `ctx.softDelete` is set, `list` and `get` must exclude
stamped rows unless `ctx.includeDeleted` is set, and `delete` must stamp the
column rather than remove the row.

`prismaAdapter` needs `provider`, a `PrismaProvider`: `"postgresql"`, `"mysql"` or
`"sqlite"`. An adapter may also implement `transaction(run)`; both built-in
adapters do, and the built-in bulk delete uses it so a failure deletes nothing.
On better-sqlite3 the Drizzle adapter's transaction is `BEGIN IMMEDIATE` and
`COMMIT` on the shared connection: it is isolated from other transactions, but a
plain query another request runs on that connection while the transaction awaits
joins it, and rolls back with it.

`list` receives `tiebreak` when a read needs a stable order across pages, as the
export does: the key columns to order by after `sort`. They come from
`introspect().keyColumns` for a composite key (a Drizzle table-level
`primaryKey()` or a Prisma `@@id`), else the primary key when it is a real column;
a resource whose key the adapter cannot see gets none, and its export is unordered.

`bullmqAdapter` takes the queue map itself, with no options object:
`bullmqAdapter({ email: emailQueue })`.

## Also exported

The parts each adapter is built from:

| Package | Also exports |
| --- | --- |
| `@flowpanel/kit/drizzle` | `introspect`, `inferSchema` |
