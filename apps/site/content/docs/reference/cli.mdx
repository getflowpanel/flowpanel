FlowPanel ships a small CLI in the `@flowpanel/cli` package. Bootstrap a
project with `pnpm dlx @flowpanel/cli init` — no install needed up front.
`init` adds `@flowpanel/cli` as a devDependency, so every later command
runs as `pnpm flowpanel <command>`. The shipped subcommands are `init`,
`migrate`, `doctor`, `eject`, `dev`, and `new`.

The CLI detects your package manager from the lockfile and uses it
throughout — `init` installs with it, `dev` launches Next.js through its
runner, and every "run this next" hint is printed in its syntax. The samples
below use pnpm; substitute your own.

<CliReference />

Every command supports `--help`; the root command supports `--version`.
Success exits `0`, validation or execution failures exit non-zero, and fatal
errors show a concise message. Set `FLOWPANEL_DEBUG=1` when you also need the
underlying stack trace.

Mutating commands build a complete filesystem plan before the first write.
`--dry-run` prints that plan; `--json` emits a machine-readable result for CI.
Writes use atomic replacement and a rollback journal, so a later failure
restores earlier files instead of leaving a half-written scaffold. Existing
files with different content are reported as conflicts, not overwritten.

## flowpanel init

<CliReference command="init" />

Detect your stack (Next.js, Drizzle/Prisma, auth helper), pick the
matching config template, install `@flowpanel/kit` + `@flowpanel/cli`,
and scaffold the wiring files. Both Drizzle and Prisma are supported in a
single command; the CLI picks based on your installed dependencies
(Drizzle wins if both are present).

The stylesheet lands at `styles/admin.css`, or at `src/styles/admin.css` when
the project keeps its source under `src/` — the CLI matches your layout rather
than always writing to the repo root.

```text
◇  Detected stack ─────────────────────────────────────╮
│  Next.js 16.3.1 · TypeScript · Drizzle · Tailwind 4  │
├──────────────────────────────────────────────────────╯
◇  7 written
◇  Wrote ─────────────────────────────────────────────────╮
│  flowpanel.config.ts                                    │
│  app/admin/[[...slug]]/page.tsx                         │
│  app/api/flowpanel/[...route]/route.ts                  │
│  app/api/flowpanel/stream/route.ts                      │
│  styles/admin.css                                       │
│  flowpanel/migrations/0001_init.sql                     │
│  app/layout.tsx (added the admin stylesheet import and  │
│  suppressHydrationWarning)                              │
├─────────────────────────────────────────────────────────╯
◇  Installed @flowpanel/kit, @flowpanel/cli
```

What varies:

- **`src/`** — every `app/` path becomes `src/app/`, and `styles/admin.css`
  becomes `src/styles/admin.css`, when the project uses a `src/` layout.
- **`app/layout.tsx`** — scaffolded when the project has none; otherwise the
  existing layout is patched with the stylesheet import. If that layout
  already imports some other CSS bundle, `init` leaves that part alone and
  prints the import line for you to add.
- **`suppressHydrationWarning`** — added to the existing layout's `<html>`
  tag whether or not the stylesheet import was. `mode: "auto"` resolves the
  theme before hydration and sets the namespaced `data-flowpanel-theme`
  marker, which the server render cannot predict; without the attribute React
  reports a hydration mismatch on every admin page.
- **`tailwind.config.ts`** — written only on Tailwind v3, and only when the
  file does not already exist. The v3 run also gets the `admin.css` v3
  variant (`@tailwind` directives instead of `@import "tailwindcss"`).
- **The install step** uses the package manager it detected — npm, pnpm, yarn
  or bun — and is skipped for packages already in your `package.json`.
- **The next-steps outro** is written in that manager's own vocabulary
  (`pnpm exec flowpanel migrate` vs `npx flowpanel migrate`, and so on).

### When `init` stops

- **No Next.js in `package.json`** — aborts, exit `1`, with the install
  command for your package manager.
- **No Drizzle and no Prisma** — aborts, exit `1`, same treatment.
- **No Tailwind** — interactive only: a confirm that defaults to **No**;
  declining aborts with exit `1` and nothing written. Under `--yes` the run
  continues.
- **No TTY and no `--yes`, `--dry-run` or `--json`** — `init` asks questions, so a non-interactive run
  without `--yes` exits `1` immediately: *"init asks questions and this run
  has no interactive terminal. Re-run with --yes to accept the detected
  defaults."* Pass `--yes` in CI.
- **A failed dependency install** does not roll back the files. It prints the
  package manager's own last lines, the commands to run by hand, and sets
  exit code `1` so the run is not mistaken for a success.

Re-running `init` is idempotent: matching generated files become `skip`.
If any target exists with different content, the plan reports a conflict and
nothing is written. Merge that file manually, then rerun. `--yes` accepts
detected paths; it does not grant permission to overwrite source.

## flowpanel migrate

<CliReference command="migrate" />

Apply SQL migrations from `flowpanel/migrations/`. The CLI dynamically
imports your `flowpanel.config.ts` (via `jiti`) so it can reach the
adapter's `db` instance and run the migration there.

```bash
$ pnpm flowpanel migrate
```

Use `--dry-run` to load the adapter and preview only migrations that are not
already recorded. Add `--json` for a stable pending/applied payload.
The CLI tracks applied IDs in `_flowpanel_migrations`.

Every command reads `.env.local` and then `.env` from the working directory
before it runs, the same order Next.js uses, so a `DATABASE_URL` that already
works for `next dev` works here too. Variables already set in the shell win, so
`DATABASE_URL=… pnpm flowpanel migrate` still overrides the file. When the
connection fails and no `DATABASE_URL` is set anywhere, the CLI says so instead
of printing a driver stack trace; `FLOWPANEL_DEBUG=1` brings the stack back.

`jiti` is loaded on demand; when it is missing the command prints the install
line for **your** package manager (`pnpm add -D jiti`, `npm install --save-dev
jiti`, …) and exits `1`.

## flowpanel doctor

<CliReference command="doctor" />

Run the wiring checks, in this order:

- Next.js ≥ 16.3 and < 17, and TypeScript installed
- an ORM the adapters support — Drizzle or Prisma
- `flowpanel.config.ts` exists
- the four generated files exist: the API route, the SSE route, the seed
  migration, and the catch-all admin page
- only one `@flowpanel/core` copy in `node_modules/.pnpm` (skipped on
  layouts without that directory rather than reported as passing)
- no destructive row/bulk action declared without a `confirm`
- `tsc --noEmit` passes

```bash
$ pnpm flowpanel doctor
$ pnpm flowpanel doctor --fix
$ pnpm flowpanel doctor --fix --dry-run
```

`--fix` creates whichever of the four generated files are missing from the
same templates `init` uses. The fix is one transaction; `--dry-run` shows it
without writing. The other failures have no auto-fix and print a hint instead.

Exit code is non-zero when any check fails — wire it into CI to catch
drift on every PR.

## flowpanel eject

<CliReference command="eject" />

Eject one of three targets — `resource`, `dashboard`, or `layout` —
into your repo. See [Customization / Eject](/docs/customization/eject).

```bash
$ pnpm flowpanel eject resource users
$ pnpm flowpanel eject dashboard "/monitoring"
$ pnpm flowpanel eject layout
```

It lists every file it wrote, then comments the matching config entry out
(uncomment to revert). Template files and the config edit are committed as one
rollback-safe transaction. Pass `--force` to explicitly replace an existing
eject target; without it, a conflict aborts before any file changes.

## flowpanel dev

<CliReference command="dev" />

Wrapper around `next dev` that also spawns `bull-board` when a
`scripts/board-server.ts` file is present and `REDIS_URL` is set.

```bash
$ pnpm flowpanel dev --port 3000
```

Both children are launched through the **detected** package manager's runner —
`pnpm exec next dev`, `npx next dev`, `yarn next dev`, `bunx next dev` — so
the local binaries resolve whichever manager installed them. Output is
prefixed `[next]` / `[board]`, and either child exiting shuts the other down.

Pass `--no-board` to skip the queue dashboard even when Redis is up. With
`REDIS_URL` set but no `scripts/board-server.ts` on disk, the board is skipped
with a one-line note rather than an error.

## flowpanel new

<CliReference command="new" />

Append a `resource(...)` entry to your existing
`flowpanel.config.ts` without re-running `init`.

```bash
$ pnpm flowpanel new posts
```

```text
└  Added resource "posts" to flowpanel.config.ts
```

It writes `resource(schema.posts, { columns: ["id"] })` into the `resources`
array — creating the array when `defineAdmin` has none — and **adds `resource`
to the existing `@flowpanel/kit` import** when the config does not already
bind that name, so the file compiles as written. Existing comments in the
array are preserved (the entry is spliced as text, not reprinted).

Before writing, a Drizzle-kind run resolves the config's `import * as schema`
line and checks that the module really exports `posts`. A miss aborts with
exit `1` and lists what the schema does export; an unverifiable case (no
`import * as schema`, an unresolvable specifier) warns and writes anyway.
A resource that already exists aborts with exit `1`.

Flags: `--table <expr>` overrides the first argument (default
`schema.<resource>`, and skips the schema check); `--kind drizzle|prisma`
toggles the template (default `drizzle`; `prisma` writes
`resource<unknown>("posts", …)`).

`--dry-run` shows the config modification without applying it. `--json`
returns the same plan/result envelope used by `init`, `doctor` and `eject`.
