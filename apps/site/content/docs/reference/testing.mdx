`@flowpanel/test` is a dev-time package: one function that walks a running
admin the way an operator does and fails the build when a page is broken. It
is not part of `@flowpanel/kit` and never reaches your application bundle.
`@flowpanel/test/widgets` is its second entry: the context a widget receives
in your admin, over rows you pass instead of a database, for a unit test of
one widget's number.

```sh
pnpm add -D @flowpanel/test @playwright/test
```

`@playwright/test` is a required peer. `@axe-core/playwright` is an optional
one — install it to turn the accessibility assertions on.

## smokeAdmin

```ts excerpt
import { test } from "@playwright/test";
import { smokeAdmin } from "@flowpanel/test";

test("the admin is healthy", async ({ page }) => {
  await smokeAdmin(page, { basePath: "/admin", a11y: true });
});
```

<ApiSignature path="../../packages/test/src/smoke-admin.ts" name="smokeAdmin" />

The walk starts at `basePath`, reads the navigation — `[data-flowpanel-nav]`,
which both shell modes render, and opens every
dashboard and resource list it links to. On each list it activates the first
row and follows wherever that resource sends it — the row's own detail page
when `rowClick: "detail"`, the URL-synced drawer when `rowClick: "drawer"`. A
row the projection cannot identify is inert, and the walk leaves it alone
rather than failing.

On a record page the walk opens every other tab as well: it reads the `data-fp-tab` keys of the
tab triggers and loads `?tab=<key>` for each tab that is not already open, so a widget that fails
only on the third tab fails the run as
`/admin/users/1?tab=activity: rendered a FlowPanel error surface`. Pass `tabs: false` to keep the
0.3.0 walk. A record that opens in a drawer is checked as the drawer first shows it; its other
tabs are not opened.

## What it asserts

| Assertion | How it fails |
| --- | --- |
| Every navigation answers below 400 | `<route>: responded 500` |
| Nothing wrote to `console.error` | `console.error: <text>` |
| No page rendered `[data-fp-error]` | `<route>: rendered a FlowPanel error surface` |
| Zero WCAG 2.2 AA violations, with `a11y` | `<route>: axe <rule> (<impact>)` |
| The navigation has at least one route | `smokeAdmin found no navigation under <basePath> …` |

`[data-fp-error]` is the attribute FlowPanel's own error surfaces carry: the card
a failed widget leaves behind, the card a failed adapter read renders, a drawer
whose payload read failed, and the error tone of the health banner. Finding one
means the page rendered, so no navigation failed, but a read underneath it did.

A walk that discovers no routes beyond the entry page is a failure, not a pass. A
`basePath` that points at the wrong mount, an unsigned-in session or a shell whose
navigation carries no `data-flowpanel-nav` would otherwise produce a green report
about a page nobody walked.

The walk waits for the `main` landmark to become visible rather than for the
network to go idle: an admin holding a realtime connection never reaches
`networkidle`.

`A11yViolation` is the element type of `SmokeAdminReport.a11yViolations`: one axe
rule, and the route it was found on.

`smokeAdmin` resolves with the report when everything passed, and throws an
`Error` whose message lists each problem and then the whole report as JSON, so
a failing run tells you which route broke without a second pass.

```ts excerpt
import { smokeAdmin } from "@flowpanel/test";

const report = await smokeAdmin(page, {
  basePath: "/admin",
  cookie: { name: "session", value: process.env.E2E_SESSION ?? "" },
  resources: ["/", "customers", "orders"],
  maxRows: 3,
  a11y: true,
});

console.log(`${report.visited.length} routes visited`);
```

`resources` takes nav segments, not paths: `"/"` is the landing dashboard and
`"customers"` is `/admin/customers`. `cookie` is added against the admin's own
origin unless you give it an explicit `domain`.

## Unit-test a widget

`widgetContext` builds the context a widget's query receives in the admin, over rows you pass
instead of a database. `resolveWidget` runs the widget the way the dashboard does and returns the
props its card receives. The pair tests a number, a link or a custom widget's props in
milliseconds, with the admin's own code.

```ts excerpt
import { resolveWidget, widgetContext } from "@flowpanel/test/widgets";
import { expect, it } from "vitest";
import { paidToday } from "@/admin/config/dashboards/money";

it("counts only today's paid invoices", async () => {
  const ctx = widgetContext({
    rows: {
      invoices: [
        { status: "paid", paidAt: new Date("2026-09-25T09:00:00Z") },
        { status: "paid", paidAt: new Date("2026-09-24T09:00:00Z") },
      ],
    },
    range: { from: new Date("2026-09-25T00:00:00Z"), to: new Date("2026-09-25T23:59:59Z") },
  });
  const { props } = await resolveWidget(paidToday, ctx);
  expect(props.value).toBe(1);
  expect(props.drilldown).toContain("/admin/invoices?f_status=paid");
});
```

`ctx.count`, `ctx.read`, `compare`, `ctx.link` and a count metric's link run exactly as in the
admin: a misspelt field throws with the name that was probably meant, an `undefined` value
counts `0` and makes `ctx.read` throw, and a filter link carries the same `f_<field>` values the
list reads. Without `admin`, every key of `rows` is a resource whose columns are the keys its
rows carry. Pass `admin` — your `defineAdmin` config — when the widget relies on what only the
admin knows: a view it links to, a dashboard, or the `reference` a record-page count infers its
filter from. Only the database is replaced then; your columns decide what a misspelling is.
Access still applies: pass `session` and `role` as your admin's `auth` would resolve them, or a
resource that checks the session reads no rows and counts `0`. It carries no tenant scope,
though: a widget scoped to the current tenant counts and reads across every tenant's rows here,
so a scope bug can pass this test while it under- or over-counts in the real admin.

`ctx.sql` returns `sql` rows, or calls your function with the statement and its bound values; a
statement nothing answers throws. `row` and `resource` make a record-page context: `ctx.id`,
`ctx.row` and `ctx.rowOf(resource)`. Formatting and labels come from `admin`, or from the
`formatting` and `labels` options. `filters` sets `ctx.filters`, the dashboard filter values a
widget branches on, as the dashboard reads them from its URL.

const ctx = headerContext({ admin });

`@flowpanel/test/widgets` is ESM-only, like `@flowpanel/next`, which it loads through
`@flowpanel/kit/next` to render the widget; the Playwright entry stays CommonJS-compatible.

### Run it in Vitest

Install Vitest — `pnpm add -D vitest` — then set up two things beyond its default config. The
entry renders widgets with `@flowpanel/next`, which Next's bundler normally resolves: inline
FlowPanel's packages so Vite resolves them too, or the first run fails with
`ERR_MODULE_NOT_FOUND` for `next/cache`. And Vitest does not read `tsconfig.json`'s `paths`, so a
config or test that imports through your `@/` alias needs `resolve.alias` (or
[`vite-tsconfig-paths`](https://www.npmjs.com/package/vite-tsconfig-paths)), the same way
`examples/ai-scraper/vitest.config.ts` resolves it:

```ts excerpt
// vitest.config.ts
import { fileURLToPath } from "node:url";
import { defineConfig } from "vitest/config";

export default defineConfig({
  resolve: { alias: { "@": fileURLToPath(new URL(".", import.meta.url)) } },
  test: { server: { deps: { inline: [/@flowpanel\//] } } },
});
```

## Playwright config

`smokeAdmin` calls `page.goto(basePath)`, which needs a `baseURL` — and in practice a
`webServer` that starts the app the walk runs against:

```ts excerpt
// playwright.config.ts
import { defineConfig } from "@playwright/test";

export default defineConfig({
  testDir: "./e2e",
  use: { baseURL: "http://localhost:3000" },
  webServer: { command: "pnpm dev", url: "http://localhost:3000", reuseExistingServer: true },
});
```

The signed-in user the walk reaches the admin as needs whatever role your `auth.role` and
`requireRole` demand — seed or promote a test user to that role, or the walk gets a redirect to
your access-denied page instead of the admin.

## Authentication

An admin behind a session cookie needs that cookie before the walk can see
anything. `cookie` suits a session your own code issues as a bare token — a dev-only session, or
one you sign yourself. A provider that issues a signed session through its own sign-in
endpoint, such as better-auth (`better-auth.session_token`, `__Secure-`-prefixed over https) or
next-auth, is not one you should hand-craft: sign in with your project's own Playwright fixture
first instead — `smokeAdmin` reuses whatever context the page already has.

```ts excerpt
import { smokeAdmin } from "@flowpanel/test";

await page.goto("/login");
await page.getByLabel("Email").fill("admin@example.com");
await page.getByLabel("Password").fill(process.env.E2E_PASSWORD ?? "");
await page.getByRole("button", { name: "Sign in" }).click();

await smokeAdmin(page);
```
