flowpanel turns a single typed config into a complete `/admin` route for
your Next.js app. This guide walks you from a fresh install to a working
dashboard.

> **Want to see it running first?** Clone the repo and start the
> `ai-scraper` example — Postgres in Docker, seeded, on `:3000`. The
> packages' `dist/` is gitignored and the example imports it, so build the
> workspace before starting the app:
>
> ```bash
> git clone https://github.com/getflowpanel/flowpanel && cd flowpanel
> pnpm install
> pnpm --filter "./packages/*" build
> cd examples/ai-scraper && pnpm docker:up && pnpm db:push && pnpm db:seed && pnpm dev
> ```
>
> Docker Desktop has to be running (`docker info` should succeed).
> `DATABASE_URL` defaults to the compose Postgres, so no `.env` is needed
> for the local run.

> **Requirements.** Next.js 15+ (App Router), React 19, Node 20+,
> Tailwind v3 or v4, and either Drizzle `>=0.36` or Prisma 5 / 6. The
> Pages router is not supported. `init` stops if it finds no Tailwind in
> `package.json` — the prompt to continue anyway defaults to No, because
> the scaffolded stylesheet is a Tailwind entry point.

## Initialize

One command installs the packages and scaffolds the `/admin` route. Run
it from your project root:

```bash
pnpm dlx @flowpanel/cli init
```

The CLI inspects your `package.json`, picks Drizzle or Prisma, installs
`@flowpanel/kit` (the runtime) and `@flowpanel/cli` (so later
`pnpm flowpanel` commands resolve a local binary), and writes the wiring
files.

It asks where your db client, schema and `getSession` live, defaulting to
whatever it found, then reports every file it touched:

```
◇  Detected stack ──────────────────────────────────╮
│  Next.js 15.5.0 · TypeScript · Drizzle · Tailwind 4  │
├──────────────────────────────────────────────────╯
◇  7 written
◇  Wrote ─────────────────────────────────────────────────╮
│  flowpanel.config.ts                                    │
│  src/app/admin/[[...slug]]/page.tsx                     │
│  src/app/api/flowpanel/[...route]/route.ts              │
│  src/app/api/flowpanel/stream/route.ts                  │
│  src/styles/admin.css                                   │
│  flowpanel/migrations/0001_init.sql                     │
│  src/app/layout.tsx (added the admin stylesheet import) │
├─────────────────────────────────────────────────────────╯
```

Pass `--yes` to take the detected defaults without being asked; it warns
about any path it had to guess.

The generated config _is_ the entire admin panel. Every resource you
list becomes a typed CRUD page; everything you don't list stays out.

## The config file

Open `flowpanel.config.ts`. This is what `init` generates (Drizzle
shown; the Prisma variant is shape-identical save the adapter import):

```ts
import { defineAdmin } from "@flowpanel/kit";
import { drizzleAdapter } from "@flowpanel/kit/drizzle";
import { db } from "@/server/lib/db";
import * as schema from "@/server/lib/db/schema";
import { getSession } from "@/server/lib/auth";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof db;
  }
  interface FlowpanelResources {
    // users: typeof schema.users.$inferSelect;
  }
}

export default defineAdmin({
  adapter: drizzleAdapter({ db, schema }),
  auth: {
    session: getSession,
    role: (s) => (s as { user?: { role?: string } } | null)?.user?.role ?? "guest",
    requireRole: "admin",
  },
  realtime: { driver: "memory" },
  theme: { brand: { name: "your-app" }, accent: "220 90% 50%", mode: "auto" },
  resources: [
    // Add `resource` to the "@flowpanel/kit" import above, then:
    // resource(schema.users, { label: "Users", columns: ["email", "name", "createdAt"] }),
  ],
});
```

**The generated `resources` array is empty** — every entry is commented
out, because the CLI cannot know which of your tables belong in an admin.
Add at least one before you run the app, or `/admin` renders with no
resources in the nav:

```ts
import { defineAdmin, resource } from "@flowpanel/kit";
// …
  resources: [
    resource(schema.users, {
      columns: ["email", "role", "createdAt"],
    }),
    resource(schema.orders, {
      columns: ["id", "status", "total"],
      filters: [{ field: "status", type: "select" }],
    }),
  ],
```

Each `resource()` call describes one table you'll manage in the admin.
The first argument is the Drizzle table, or — for Prisma — the model name
as a string, e.g. `resource("User", { … })`. Prisma model names are
PascalCase and the name is also the URL slug, so `resource("User", …)`
lives at `/admin/User`; pass `name: "users"` in the options to choose the
slug yourself.

Columns, filters and actions are type-checked against the row shape
**when FlowPanel can infer one**. A Drizzle table ref infers it from
`$inferSelect` automatically. A Prisma string ref has no row type to
infer, so those fields stay plain `string` until you fill in the
`FlowpanelResources` entry the template leaves commented:

```ts
declare module "@flowpanel/kit" {
  interface FlowpanelResources {
    User: import("@prisma/client").User;
  }
}
```

The `FlowpanelTypes` block binds `typeof db` into `WidgetContext`, so
`ctx.db` in dashboards and actions is your real, typed client.

### If you don't have a session helper yet

The template imports `getSession` from your app because that is what a real
admin needs. To get to a rendered page before wiring auth, swap the whole
`auth` block for `devAuth()`:

```ts
import { defineAdmin, devAuth } from "@flowpanel/kit";

export default defineAdmin({
  adapter: drizzleAdapter({ db, schema }),
  auth: devAuth(),           // every request is a signed-in "admin"
  // …
});
```

`devAuth(role = "admin")` returns an `AuthConfig` whose session is always
`{ id: "dev" }` and whose `role()` always returns `role`. It is also exported
from `@flowpanel/kit/auth` alongside `withClerk` / `withLucia` /
`withNextAuth`.

<Callout type="warn">
`devAuth()` authenticates nobody. It sets no `requireRole`, so the admin still
answers anonymous requests, and the "no access control" development warning
still fires — deliberately, because that warning is the thing that stops this
reaching production. Replace it with a real provider (see
[Authenticate with Clerk](/docs/guides/auth-with-clerk)) before you deploy.
</Callout>

## Mount the route

`flowpanel init` already wrote two files:

```ts
// app/admin/[[...slug]]/page.tsx
import { Flowpanel } from "@flowpanel/kit/next";
import config from "@/flowpanel.config";

export default Flowpanel(config);
```

```ts
// app/api/flowpanel/[...route]/route.ts
import { handlers } from "@flowpanel/kit/next";
import config from "@/flowpanel.config";

export const { GET, POST } = handlers(config);
export const runtime = "nodejs";
```

The page renders every `/admin/...` URL via a single catch-all RSC. The
API route handles the drawer fetch and bulk-action submissions. A third
file, `app/api/flowpanel/stream/route.ts`, mounts the SSE channel for
realtime — generated automatically by `init`.

## Run

`init` also wrote `flowpanel/migrations/0001_init.sql`, which creates the
migration-tracking table and `flowpanel_audit_log`. Apply it once, then
start the dev server:

```bash
pnpm flowpanel migrate
pnpm dev
```

Open `localhost:3000/admin`. Each resource you listed gets its own page
with CRUD, pagination and filters, driven entirely by the config you just
wrote. With an empty `resources` array, `/admin` shows a welcome screen
with a copy-paste snippet for your first resource instead of a nav.

The migration's SQL is Postgres-flavoured — adjust it by hand for MySQL
or SQLite. And `flowpanel_audit_log` is only a table: FlowPanel writes
**nothing** to it until you point `audit.sink` at it, so a fresh install
leaves it empty forever. See
[Configuration](/docs/core-concepts/configuration).
