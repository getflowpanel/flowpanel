This tutorial builds the admin a founder opens every morning. It uses the domain of the
[ScrapeAI example](https://github.com/getflowpanel/flowpanel/tree/main/examples/ai-scraper):
customers set up monitors, monitors produce runs, and runs find listings on marketplaces. Each
step ends with what you should see. It assumes a Next.js 16 app with a Drizzle schema and
better-auth; [Getting started](/docs/introduction/getting-started) covers Prisma and every
`init` option.

## 1. Install

```bash
pnpm dlx @flowpanel/cli init
pnpm flowpanel migrate
pnpm dev
```

You should see `/admin` with an empty navigation. `init` leaves `resources` empty on purpose:
only you know which tables belong in the admin.

## 2. Take types from your schema and your auth

`init` already told FlowPanel where your database, schema and session types come from. The
config it wrote declares the first two:

```ts excerpt
// flowpanel.config.ts
declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof db;
    schema: typeof schema;
  }
}
```

With better-auth, when your auth module exports the instance and no `getSession`, the session
module it wrote next to the config (`server/lib/flowpanel-session.ts`) declares the third and wraps your auth instance in the
better-auth preset:

```ts excerpt
// server/lib/flowpanel-session.ts
import { withBetterAuth } from "@flowpanel/kit/auth";
import { auth } from "@/src/lib/auth";

export const flowpanelAuth = withBetterAuth({ auth, requireRole: "admin" });
export const getSession = flowpanelAuth.session;

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    session: typeof auth.$Infer.Session;
  }
}
```

Every resource name, every row and `ctx.session` is now typed from sources you already own, and
there is no list of resources to keep in sync. The preset reads the role from
`session.user.role` and the actor id for the audit trail from `session.user.id`, so the config's
whole `auth` block becomes one line: import `flowpanelAuth` instead of `getSession`, and write
`auth: flowpanelAuth`.

You should see a type error the moment a config names a table that does not exist.

## 3. One resource per file

Move the config `init` wrote into `src/admin/config/index.ts` and leave a one-line re-export at
the root, so the admin route and the CLI both still find it:

```bash
mkdir -p src/admin/config
git mv flowpanel.config.ts src/admin/config/index.ts
echo 'export { default } from "./src/admin/config";' > flowpanel.config.ts
```

If the moved file imports anything by a relative path, fix those paths; the `@/…` aliases `init`
writes need no change. Then let `flowpanel new` write one file per table, the tables others
point at first:

```bash
pnpm flowpanel new customers --dir src/admin/config/resources
pnpm flowpanel new monitors --dir src/admin/config/resources
pnpm flowpanel new runs --dir src/admin/config/resources
pnpm flowpanel new invoices --dir src/admin/config/resources --hidden
```

Each command follows the re-export to your schema, reads the table, picks columns by type, and
adds the export to `src/admin/config/resources/index.ts`. A foreign key becomes a `reference`
labelled by the target's `name` (else its `title`, else its `email`) once the target has a file of
its own — which is why `customers` goes first; a key to a table the admin does not show stays a
plain column, and the command says so. `--hidden` keeps invoices out of the navigation — they
appear on the customer's page instead. Hand the array to `defineAdmin`:

```ts excerpt
// src/admin/config/index.ts
import { resources } from "./resources";

export default defineAdmin({
  // …everything init wrote…
  resources,
});
```

You should see Customers, Monitors and Runs in the navigation, each a list, and every run
naming its monitor. The dev server picks up config changes without a restart.

## 4. Declare each enum once

```ts excerpt
// src/admin/config/enums.ts
import { enumOf } from "@flowpanel/kit";
import { accountStatus, planTier, runStatus } from "@/src/db/schema";

export const RunStatus = enumOf(runStatus.enumValues, {
  queued: ["Queued", "muted"],
  running: ["Running", "info"],
  success: ["Success", "ok"],
  failed: ["Failed", "err"],
});

export const Plan = enumOf(planTier.enumValues, {
  free: ["Free", "muted"],
  starter: ["Starter", "info"],
  pro: ["Pro", "accent"],
  business: ["Business", "accent"],
});

export const AccountStatus = enumOf(accountStatus.enumValues, {
  active: ["Active", "ok"],
  trialing: ["Trialing", "info"],
  past_due: ["Past due", "err"],
  canceled: ["Canceled", "muted"],
});

export const Site = enumOf({
  amazon: "Amazon",
  best_buy: "Best Buy",
  ebay: "eBay",
  newegg: "Newegg",
  walmart: "Walmart",
  media_markt: "MediaMarkt",
  mercado_libre: "Mercado Libre",
});
```

`listings.site` is a text column, so `Site` lists its values itself; they are the seven
marketplaces the example seeds (`examples/ai-scraper/src/demo/data/types.ts`, `MARKETPLACES`).
For the three database enums, a value the database enum has and the map lacks is a compile
error. `flowpanel new` wrote an `enumOf` stub into each resource file; delete it and use the
shared enum wherever the column appears:

```ts excerpt
columns: [{ field: "status", format: RunStatus.format }],
filters: [{ field: "status", type: "multiselect" }],
```

The filter needs no `options`: a select on a column formatted by an enum lists the enum's labels,
in the order you declared them. `RunStatus.label(value)`, `.tone(value)` and
`.badge(value, { href })` serve widgets and record headers.

You should see coloured status badges and a status filter with four labels.

## 5. A dashboard, starting from the right data call

Every widget receives `ctx`. Pick the call by what you need:

| You want | Use | Scope, access, soft delete applied |
|---|---|---|
| how many rows | `ctx.count(resource, where, { range })` | yes |
| the rows themselves | `ctx.read(resource, { where, range })` | yes |
| the record on this card | `ctx.rowOf(resource)` | yes |
| a number only SQL can define | ``ctx.sql`…` `` | no — add the predicates |
| your ORM | `ctx.db` | no |
| one result shared by several widgets | `ctx.query(fn)` around any of the above | — |

Start with a strip of numbers that compare themselves with the period before:

```ts excerpt
// src/admin/config/dashboards/overview.ts
import { dashboard, metric } from "@flowpanel/kit";

export const overview = dashboard({
  path: "/",
  label: "Overview",
  dateRange: { preset: "today", presets: ["today", "yesterday", "last7d", "last30d"] },
  refresh: "60s",
  sections: [
    {
      variant: "strip",
      widgets: [
        metric("Runs", { count: "runs", range: "startedAt" }, { compare: true }),
        metric(
          "Failed runs",
          { count: "runs", where: { status: "failed" }, range: "startedAt" },
          { compare: { goodWhen: "down" } },
        ),
        metric("New customers", { count: "customers", range: "createdAt" }, { compare: true }),
      ],
    },
  ],
});
```

Add `dashboards: [overview]` to `defineAdmin`. Each number links to its own rows, with the same
filter and the same period, and shows its change against the previous period. The period
reaches the list through a `daterange` filter, so give each counted date one — `startedAt` on
runs, `createdAt` on customers, and `paidAt` on invoices for step 8:

```ts excerpt
// src/admin/config/resources/runs.ts
filters: [
  { field: "status", type: "multiselect" },
  { field: "startedAt", type: "daterange" },
],
```

`defineAdmin` refuses a `range` that names no `daterange` filter of the counted resource, and
says which one is missing.

You should see three numbers in one band, each with a change and a link that opens the list
filtered to exactly the rows it counted.

## 6. One SQL statement, three widgets

Some numbers only SQL can define. Write the statement once and let FlowPanel bucket, rank and
compare it. Charts render with Recharts, an optional peer, so run `pnpm add recharts` first:

```ts excerpt
// src/admin/config/dashboards/marketplaces.ts
import { bars, breakdown, dashboard, series, type WidgetContext } from "@flowpanel/kit";
import { lineChart } from "@flowpanel/kit/charts";
import { Site } from "../enums";

const listingsFound = (c: WidgetContext) =>
  c.sql<{ at: Date; site: string }>`
    select l.scraped_at as at, l.site
    from listings l
    where l.scraped_at >= ${c.dateRange.from} and l.scraped_at < ${c.dateRange.to}
      and (${c.filters.site ?? null}::text is null or l.site = ${c.filters.site ?? null})`;

const marketplace = { key: "site", label: "Marketplace", options: Site };

export const marketplaces = dashboard({
  path: "/marketplaces",
  label: "Marketplaces",
  dateRange: { preset: "last7d", presets: ["today", "last7d", "last30d"] },
  filters: [marketplace],
  sections: [
    {
      widgets: [
        bars({
          label: "Listings by marketplace",
          query: async (c) => breakdown(await c.query(listingsFound), { by: "site", labels: Site }),
          share: true,
          compare: true,
          filter: "site",
          span: 4,
        }),
        lineChart(
          "Listings per day",
          async (c) =>
            series(await c.query(listingsFound), c.dateRange, { at: "at", by: "site", grain: "day" }),
          { x: "date", labels: Site, span: 8 },
        ),
      ],
    },
  ],
});
```

Add `marketplaces` to `dashboards`. `c.query(listingsFound)` runs the statement once per
request, and once more for the previous period that `compare` asks for. `series` buckets the
rows into days in the admin's time zone and fills the gaps; `breakdown` ranks them with each
one's share. `ctx.sql` applies no scope, so a multi-tenant admin adds its tenant predicate to
the statement itself.

You should see bars with shares and changes and a line per marketplace. Click a bar and the
whole page narrows to that marketplace; the Marketplace select beside the date picker shows it.

## 7. Status at a glance

A tracker answers "is it healthy right now": one row per marketplace, one block per hour. It
lives on the Marketplaces dashboard, so it shares `listingsFound` and the Marketplace filter:

```ts excerpt
import { type Threshold, tracker } from "@flowpanel/kit";

const QUIET: Threshold = { warn: 5, err: 1, goodWhen: "up" };

const listingsByHour = tracker({
  label: "Listings found · 24 h",
  query: listingsFound,
  at: "at",
  by: "site",
  labels: Site,
  tones: QUIET,
  filter: "site",
  span: 12,
});
```

Append `{ widgets: [listingsByHour] }` to the `sections` of `marketplaces` from step 6. The
tracker ignores the date picker: its window is the last 24 hours, and `ctx.dateRange` inside
`listingsFound` is that window. With `goodWhen: "up"`, an hour with 5 listings or fewer is a
warning and an hour with one is an error; an hour with none stays grey, because there is
nothing to judge.

You should see one row per marketplace, 24 hourly blocks each, coloured by how many listings
that hour found; a click on a row narrows the whole page to that marketplace.

## 8. A record page

Put the customer's page in its own file. `DetailOptions` types every callback by the resource's
row:

```ts excerpt
// src/admin/config/resources/customer-card.ts
import {
  checklist,
  type DetailOptions,
  enumOf,
  filled,
  kv,
  metric,
  related,
  type RowOf,
  timeline,
} from "@flowpanel/kit";
import { AccountStatus, Plan } from "../enums";

const Activity = enumOf({
  monitor: ["Monitor added", "info"],
  paid: ["Invoice paid", "ok"],
});

export const paidInvoices = metric(
  "Paid invoices",
  { count: "invoices", where: { status: "paid" }, range: "paidAt" },
  { compare: true },
);

export const customerCard = {
  title: (c) => c.company ?? c.email,
  subtitle: (c, { format }) => `Customer since ${format.date(c.createdAt)}`,
  badge: (c) => [
    AccountStatus.badge(c.status, { href: { resource: "customers", filter: { status: c.status } } }),
    Plan.badge(c.plan),
  ],
  dateRange: { preset: "last30d", presets: ["last7d", "last30d", "QTD"] },
  stats: [metric("Monitors", { count: "monitors" }), paidInvoices],
  aside: [
    kv({
      label: "Account",
      columns: 1,
      items: [
        { label: "Email", field: "email" },
        { label: "Plan", field: "plan", format: Plan.format },
        { label: "Last seen", field: "lastSeenAt", format: "relative" },
      ],
    }),
    checklist({
      label: "Profile",
      items: async (c) => filled(c.rowOf("customers"), { name: "Name", company: "Company" }),
    }),
  ],
  tabs: [
    {
      key: "activity",
      label: "Activity",
      widgets: [
        timeline({
          kinds: Activity,
          sources: [
            timeline.source("monitors", { kind: "monitor", at: "createdAt", title: (m) => m.name }),
            timeline.source("invoices", {
              kind: "paid",
              at: "paidAt",
              title: (i, _refs, c) => c.format.money(i.amountCents, { scale: 100 }),
            }),
          ],
        }),
      ],
    },
    related("monitors", { count: true }),
    related("invoices", { count: true, sort: { field: "createdAt", dir: "desc" } }),
  ],
} satisfies DetailOptions<RowOf<"customers">>;
```

Pass it as `detail: customerCard` on the customers resource. The strip and the side column stay
on every tab; the related tabs find their filter from the `customerId` reference `flowpanel new`
wrote, and show their row counts in the tab labels. `paidInvoices` has a name of its own so a
unit test can import it (step 11).

You should see the customer's status and plan as badges, their monitor count and the invoices
paid in the picked period,
their account facts beside the tabs, and an activity feed grouped by day. More in
[Build a record page](/docs/build/detail-cards).

## 9. A custom widget for what config cannot say

A widget no built-in card fits is a server component built from kit atoms:

```tsx excerpt
// src/admin/ui/CrawlQueue.tsx
import { type Tone, toneTextClass } from "@flowpanel/kit";
import { StatusDot } from "@flowpanel/kit/react";

export function CrawlQueue({ waiting, failed }: { waiting: number; failed: number }) {
  const tone: Tone = failed > 0 ? "err" : waiting > 100 ? "warn" : "ok";
  return (
    <p className="flex items-center gap-2 text-sm">
      <StatusDot tone={tone} />
      <span className={toneTextClass[tone]}>
        {waiting} waiting · {failed} failed
      </span>
    </p>
  );
}
```

`custom()` puts it in a dashboard section. `queueCounts` is your own function that returns
`{ waiting, failed }` — from your job queue's counts, for example:

```ts excerpt
const crawlQueue = custom(CrawlQueue, (c) => c.query(queueCounts), {
  label: "Crawl queue",
  realtime: "pipeline",
  span: 4,
});
```

Add `{ widgets: [crawlQueue] }` to the overview's `sections`.

You should see a card titled "Crawl queue" that looks like its neighbours. The
[custom widget guide](/docs/customization/custom-widgets) covers links, formatting, the Tailwind
token bridge and tests.

## 10. Live updates from the worker

The worker that runs crawls tells the admin when something changed. Install `ioredis`, and keep
the realtime options in one module that both the admin config and the worker import:

```ts excerpt
// src/shared/realtime.ts
import type { PublisherOptions } from "@flowpanel/kit";

export const realtime = {
  driver: "redis",
  url: process.env.REDIS_URL!,
  keyPrefix: `scrapeai-${process.env.NODE_ENV}`,
} satisfies PublisherOptions;
```

Pass it to `defineAdmin` as `realtime`, in place of the memory driver `init` wrote. Then publish
from the worker:

```ts excerpt
// worker/admin-events.ts
import { createPublisher } from "@flowpanel/kit/publish";
import { realtime } from "@/src/shared/realtime";

export const adminEvents = createPublisher(realtime);

await adminEvents.resource("runs", { id: run.id });
await adminEvents.publish("pipeline");
```

Both sides use one Redis URL and one prefix. A Redis error never fails the crawl. In the admin,
`realtime: { resource: "runs" }` on a widget, or `realtime: true` on the runs resource,
re-renders when that event arrives; the crawl queue card from step 9 listens on `"pipeline"`.

You should see the runs list (with `realtime: true`) and the crawl queue card update while a
crawl runs, without a reload. See
[Realtime with Redis](/docs/guides/realtime-with-redis#publish-from-an-external-worker).

## 11. Test the whole admin, and one number

Install the test package and Playwright with `pnpm add -D @flowpanel/test @playwright/test`,
then walk the admin:

```ts excerpt
// e2e/admin.spec.ts
import { test } from "@playwright/test";
import { smokeAdmin } from "@flowpanel/test";

test("the admin is healthy", async ({ page }) => {
  await smokeAdmin(page, {
    basePath: "/admin",
    cookie: { name: "session", value: process.env.E2E_SESSION ?? "" },
  });
});
```

The walk opens every dashboard, every list, the first record of each and every tab of that
record, and fails on an error card, a console error or a 4xx/5xx. A single number gets a unit
test with `widgetContext({ admin, rows })` and `resolveWidget` from `@flowpanel/test/widgets`:
your admin's own code over rows you pass; see
[Testing](/docs/reference/testing#unit-test-a-widget), and
[Build a record page](/docs/build/detail-cards#test-the-card) for a test of `paidInvoices`. In
Vitest it needs one line of config, shown in
[Run it in Vitest](/docs/reference/testing#run-it-in-vitest).

You should see a green run. Break a widget on the Monitors tab and the failure names that tab's
URL, such as `/admin/customers/1?tab=monitors`.

## 12. Ship

Work through the [production readiness checklist](/docs/guides/production-readiness): a real
session provider, roles, tenant scope, the Redis realtime driver and a rate limit. Then deploy
the app as you deploy any Next.js app — the admin is a route of it.

You should see every item of the checklist ticked, the admin at `/admin` on the deployed URL
behind your sign-in, and `smokeAdmin` green against that URL.
