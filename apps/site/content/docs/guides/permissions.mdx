Every rule is checked on the server route; the UI only hides what a role cannot use. Rules narrow from the whole admin down to a field.

## The whole admin

`auth.requireRole` protects every page, API handler and stream. See [Authentication](/docs/guides/authentication).

```ts excerpt
auth: {
  session: getSession,
  role: (session) => session?.user?.role ?? "guest",
  requireRole: ["admin", "support"],
}
```

## A dashboard, page or queue

`requireRole` on any of them hides it from the navigation and rejects its direct route.

## A resource or action

`access` on a resource sets a rule per operation: `read`, `create`, `update`, `delete`. A resource the caller may not `read` leaves the navigation and rejects its routes.

An action with its own `access` runs under that rule alone, the same one that shows it in the UI. An action without one runs under the resource's `update` rule.

## Fields

Form fields take `requireRole`, `readOnly` and `hidden`. The server rejects a submitted field the operation may not write.

```ts excerpt
update: {
  fields: [
    { name: "name", required: true },
    { name: "role", type: "select", options: ["member", "admin"], requireRole: "admin" },
    { name: "createdAt", readOnly: true },
  ],
}
```

`fieldAccess` on a resource sets read and write rules per field.

## Rows

An action's `hidden(row)` removes it for that row and its route rejects the pair; `disabled(row)` shows it with a reason. For tenant isolation use [scope](/docs/guides/multi-tenant-scope), which applies to every read and write by ID.

## Read-only mode

`readOnly: true` on the admin turns off every generated mutation, for maintenance or an incident.

## Verify

For each role, request the page and the route behind it: list and get, create, update and delete, actions, import, drawer tabs and queues. Include a crafted write with a read-only field. Authorization runs before input validation, so a denied caller learns nothing about the form.
