Use this recipe after deciding that the single-process memory driver is insufficient. It keeps the browser SSE route unchanged and replaces the process-local publisher with Redis pub/sub.

## Install Redis support

```bash
pnpm add ioredis
```

Provide `REDIS_URL` through the deployment environment. Use TLS and credentials appropriate for the Redis provider.

## Configure the publisher

```ts excerpt
export default defineAdmin({
  adapter,
  auth,
  realtime: {
    driver: "redis",
    url: process.env.REDIS_URL,
    keyPrefix: "myapp-production",
  },
  resources,
});
```

Use a distinct key prefix for every application and environment sharing the same Redis service. Resources or widgets subscribe to their normal application channel names; the prefix is applied on the transport.

## Publish from an external worker

A worker, a cron job or a one-off script publishes through `@flowpanel/kit/publish`. It is the
whole realtime client: no admin config, no adapter, no Next.js — one connection and the wire
format.

Give it the admin's own `realtime` options, so the worker and the admin cannot disagree about the
Redis URL or the key prefix:

```ts excerpt
// src/shared/realtime.ts — imported by the admin config and by the worker
import type { PublisherOptions } from "@flowpanel/kit";

export const realtime = {
  driver: "redis",
  url: process.env.REDIS_URL!,
  keyPrefix: `myapp-${process.env.NODE_ENV}`,
} satisfies PublisherOptions;
```

```ts excerpt
// worker/admin-events.ts
import { createPublisher } from "@flowpanel/kit/publish";
import { realtime } from "@/shared/realtime";

export const adminEvents = createPublisher({
  ...realtime,
  onError: (err, channel) => logger.warn({ err, channel }, "admin realtime publish failed"),
});

await adminEvents.resource("orders", { id: order.id });
await adminEvents.publish("pipeline");
```

`resource("orders", { id })` tells every open list and record page of `orders` that its rows
changed — the event an admin action sends. `action` defaults to `"update"`; pass `"create"` or
`"delete"` when that is what happened. `publish(channel)` sends on a channel of your own, which a
widget subscribes to with `realtime: "pipeline"`. `resource()` does not check the name against
your schema, and the SSE route ignores a channel no page subscribes to, so a misspelt name
refreshes nothing.

A Redis failure never fails the job that published: `publish` and `resource` resolve, and the
error reaches `onError`, or is logged once per error kind when there is none. Publishing after
`close()` still throws, because that is a bug in the caller. Create the publisher once per
process and `close()` it on shutdown; nothing connects until the first publish.

When the worker already owns a configured Redis client — TLS, a sentinel, a retry strategy, a
BullMQ connection — hand it over instead of a URL; any `ioredis` instance fits, and it stays yours
to close:

```ts excerpt
import { createPublisher } from "@flowpanel/kit/publish";
import { redis } from "./redis";

const events = createPublisher({ redis, keyPrefix: realtime.keyPrefix });
```

Import `createPublisher` from `@flowpanel/kit/publish`; the admin builds its own transport, and
`createPublisher` from the `@flowpanel/kit` root is a deprecated alias of that transport factory,
`createRealtimeTransport`, which rejects on a Redis error.

Inside the admin itself nothing changes: `ctx.publish` in an action, or `publishResource` from
`@flowpanel/kit/server`, already use the publisher `defineAdmin` configured.

## Verify across instances

Run two application instances against the same Redis key prefix. Connect a browser to one, perform a mutation through the other, and confirm the browser refetches. Repeat with a worker publication. If local same-instance updates work but this test fails, inspect the prefix, the Redis URL, and network/TLS settings. FlowPanel also warns on startup when it resolves the memory driver while `REDIS_URL` is set in the environment, which is the configuration that produces exactly this symptom.

## Production notes

Redis publication distributes refresh signals; it does not make SSE durable. Monitor publish errors and reconnects, and decide whether a failed post-commit notification should alert, retry, or wait for the next user refresh.
