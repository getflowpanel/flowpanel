---
title: Realtime with Redis
description: Turn on live list updates across multiple Next.js instances with the Redis SSE driver — one config field.
---

flowpanel pushes live updates to open browsers over Server-Sent Events. On a
single instance the default `memory` driver works out of the box. The moment
you run **more than one Next.js instance**, you need the `redis` driver so an
event raised on one instance reaches a browser connected to another.

> For the full production checklist (proxy buffering, TLS, LB idle timeouts,
> rolling-deploy hygiene), see
> [Realtime in production](/docs/core-concepts/realtime-multi-instance).

## 1. Enable realtime on a resource

Opt a resource into live updates with `realtime: true`. Lists for that
resource refresh automatically when a row is created, updated, or deleted:

```ts
import { resource } from "@flowpanel/kit";
import * as schema from "@/db/schema";

resource(schema.orders, {
  columns: ["id", "status", "total"],
  realtime: true,
});
```

## 2. Install `ioredis`

The Redis driver loads `ioredis` dynamically, and it is an **optional** peer
dependency — a kit install does not pull it in:

```bash
pnpm add ioredis
```

Without it, the first publish throws
`ioredis is not installed — required for realtime.driver='redis'.`

## 3. Point the publisher at Redis

`realtime` takes the publisher options directly. Switch the driver to
`redis` and pass your connection URL:

```ts
import { defineAdmin } from "@flowpanel/kit";

export default defineAdmin({
  // …adapter, auth, resources…
  realtime: {
    driver: "redis",
    url: process.env.REDIS_URL!,
    // Optional: namespaces channels so multiple admins can share one Redis.
    // Defaults to "flowpanel".
    keyPrefix: "fp",
  },
});
```

That's the entire switch for anything served by `Flowpanel(config)` or
`handlers(config)` — both bind the publisher to this config, so every
`resource.realtime: true` and every in-request `publishResource(...)` fans out
over Redis pub/sub instead of an in-process emitter. Processes that run
neither need one extra line; see step 4. The
`app/api/flowpanel/stream/route.ts` SSE endpoint — generated by
`flowpanel init` — is unchanged.

flowpanel publishes only the **resource name + action** over Redis, never row
contents. The payload is `{ action, id? }`, so the row **id does** travel —
it is the row's identifier, not its contents. Browsers receive the ping and
re-fetch the updated rows over HTTPS, so Redis is the notification channel,
not the source of truth.

## 4. Publish custom events (optional)

For dashboards or background jobs, push your own resource event from a route
handler or a worker. Inside a FlowPanel action, prefer `ctx.publish` — it is
the same publisher, already bound.

```ts
import { publishResource } from "@flowpanel/kit/next";

await db.update(schema.orders).set({ status: "shipped" }).where(/* … */);
await publishResource("orders", { action: "update", id: orderId });
```

`publishResource("orders", …)` publishes to the channel `resource.orders` —
that `resource.` prefix is what a resource's `realtime: true` subscribes to,
and what a widget's `realtime` option has to name in full.

### Bind the publisher outside the admin's own routes

`bindPublisher(config)` is what points `publish` / `publishResource` at your
`realtime` options. `handlers()`, `Flowpanel()` and `stream()` call it for
you. Anywhere else, call it yourself — once, at module scope:

```ts title="scripts/worker.ts"
import { bindPublisher, publishResource } from "@flowpanel/kit/next";
import config from "@/flowpanel.config";

bindPublisher(config);

// …later, per job
await publishResource("orders", { action: "update", id: orderId });
```

That covers standalone workers and crons — and **your own route handlers**
too. On serverless each route is its own cold-startable instance, so a
`app/api/webhooks/stripe/route.ts` that publishes has to bind in that module
as well; it does not inherit the binding from the admin's catch-all:

```ts title="app/api/webhooks/stripe/route.ts"
import { bindPublisher, publishResource } from "@flowpanel/kit/next";
import config from "@/flowpanel.config";

bindPublisher(config);

export async function POST(req: Request) {
  // …handle the webhook
  await publishResource("orders", { action: "update", id });
  return Response.json({ ok: true });
}
```

Binding twice is harmless — the second call is a no-op once a publisher
exists. Skipping it is not: the publish falls back to an in-memory publisher
no other process can see, logs one warning, and the event reaches nobody.

`@flowpanel/kit/server` re-exports the same three functions against the same
process-wide store, so `import { publish } from "@flowpanel/kit/server"` and
`from "@flowpanel/kit/next"` are interchangeable.

## When the `memory` driver is enough

- `next dev`
- A single-container / single-instance deployment
- Previews where cross-instance fan-out doesn't matter

In those cases leave `realtime` as `{ driver: "memory" }` (or omit it — memory
is the default).
