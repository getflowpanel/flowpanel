A committed change publishes a small event; lists and widgets subscribed to its channel refetch through their normal authorized query. Events reach the browser over Server-Sent Events. They are refresh signals, not row data, and not a durable log: a reconnect refetches current state.

## Subscribe

`realtime: true` on a resource refreshes its list. A record page does not subscribe on its own; give its widgets their own `realtime: { resource: "orders" }`. A widget takes a channel name, `{ resource: "orders" }`, or a list of them:

```ts
metric("Open orders", openOrders, { realtime: { resource: "orders" } });
custom(Pipeline, pipelineProps, { realtime: "pipeline" });
```

A channel name other than `resource.<name>` is your own; declare it in `realtime.channels` (below).

Generated creates, updates and deletes publish on their resource automatically. An action publishes when it returns `refresh: true` (its resource) or channels (`refresh: "pipeline"` or a list). In your own server code, call `ctx.publish` in an action, or `publishResource` and `publish` from `@flowpanel/kit/next`.

## Declare your own channels

The stream serves `resource.<name>` channels to whoever may read that resource. Every other channel must be declared, with who may subscribe:

```ts
import type { RealtimeConfig } from "@flowpanel/kit";

export const realtime = {
  driver: "redis",
  url: process.env.REDIS_URL,
  channels: {
    pipeline: { access: ["admin", "ops"] },
    deploys: { tenantSafe: true },
  },
} satisfies RealtimeConfig;
```

Pass it to `defineAdmin` as `realtime`. `access` takes the same rule as a resource. Without it, everyone `auth.access` admits may subscribe. The stream refuses an undeclared channel, and `defineAdmin` refuses a widget, dashboard or list that subscribes to one, naming it.

With an admin-wide `scope`, an event on your own channel reaches the browser as `{}`: the subscribed widget still refetches through its scoped query, but no payload crosses tenants. Set `tenantSafe: true` only when the payload names nothing tenant-specific, such as a deploy finishing. A tenant-scoped resource's own events keep only their `action`.

## Choose the driver

The default memory driver reaches only the process that published. Use Redis when more than one process serves the admin, during overlapping deploys, or when a worker publishes.

```bash
pnpm add ioredis
```

```ts
import { defineAdmin } from "@flowpanel/kit";
import { flowpanelAuth } from "@/server/lib/flowpanel-session";

export default defineAdmin({
  adapter,
  auth: flowpanelAuth,
  realtime: {
    driver: "redis",
    url: process.env.REDIS_URL,
    keyPrefix: "myapp-production",
  },
  resources,
});
```

Use a distinct `keyPrefix` per app and environment sharing one Redis. FlowPanel warns on the first request when it runs the memory driver while `REDIS_URL` is set.

## Publish from a worker

A worker, cron job or script imports only `@flowpanel/kit/publish`: no admin config, adapter or Next.js. Share the admin's `realtime` options in one module that the admin config and the worker both import, so both sides use the same URL and prefix:

```ts
// src/shared/realtime.ts
import type { PublisherOptions } from "@flowpanel/kit";

export const realtime = {
  driver: "redis",
  url: process.env.REDIS_URL!,
  keyPrefix: "myapp",
} satisfies PublisherOptions;
```

Do not build the prefix from `NODE_ENV`. A worker started with `tsx` or `node` leaves it unset, so it would publish under `myapp-undefined` while the app listens under `myapp-development`, and FlowPanel warns about a prefix that contains `undefined`. When staging and production share one Redis, read the prefix from a variable that both the app and the worker set.

```ts
// worker/admin-events.ts
import { createPublisher } from "@flowpanel/kit/publish";
import { realtime } from "@/shared/realtime";

export const adminEvents = createPublisher({
  ...realtime,
  onError: (err, channel) => console.warn("admin realtime publish failed", { channel, err }),
});

export async function orderShipped(order: { id: number }): Promise<void> {
  await adminEvents.resource("orders", { id: order.id });
  await adminEvents.publish("pipeline");
}
```

Run the worker with `tsx`, `node` or your job runner as it is. `@flowpanel/kit/publish` loads both as an ES module and through `require`, so a project without `"type": "module"`, such as a fresh `create-next-app`, needs no `.mts` file.

`resource(name, { id })` refreshes that resource's lists and the widgets subscribed to it; `action` defaults to `"update"`. `publish(channel)` sends on your own channel. Names are not checked, so a misspelt one refreshes nothing.

A Redis error never fails the job: the call resolves and the error goes to `onError`, or is logged once per error kind. With Redis down, a publish over a connection made from `url` gives up after one reconnect, in a second or two rather than a minute. A client you pass in keeps its own options; set `maxRetriesPerRequest: 1` on it for the same. Create the publisher once per process and `close()` it on shutdown. To reuse a configured `ioredis` client, pass it instead of a URL: `createPublisher({ redis, keyPrefix })`.

## Production

- The stream route checks `auth.access` itself. If middleware protects the admin (Clerk, a proxy), include the stream path.
- Turn off reverse-proxy buffering for the stream path.
- Set proxy and load-balancer idle timeouts above 15 s, the stream heartbeat.
- Allow enough long-lived connections for your operators. One user may hold 10 streams at once; the next answers `429`.
- A stream ends after 15 minutes and the browser reconnects through `auth.access`, so a user whose access is revoked stops receiving events within that time. `stream(config, { maxPerActor, maxAgeMs })` changes both.
- Monitor reconnects, stream errors and publish failures.

## Verify end to end

Open one resource in two browsers, change a row in one and watch the other refetch. With several instances, connect the browser to one and change the row through another, then repeat with a worker publish.
