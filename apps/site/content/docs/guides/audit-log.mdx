With the audit log on, every write through the admin records one event: who acted, what ran, which record, the fields that changed with their old and new values, and when. Each record page gets a **History** tab, and the admin gets an **Audit log** page.

## Turn it on

Create the table once with the migration `init` wrote, then turn auditing on:

```bash
pnpm flowpanel migrate
```

```ts as="AdminDefinition"
audit: { enabled: true },
```

`flowpanel migrate` creates `flowpanel_audit_log` through the database client in `flowpanel.config.ts`, with SQL for PostgreSQL, MySQL or SQLite. Both shipped adapters write to it through the same client. With a custom adapter that has no `auditLog`, `defineAdmin` refuses to start until you pass a `sink`.

## What is recorded

Creates, updates (form and inline), deletes, restores, exports, and row, bulk, drawer and dashboard actions each record one event after the write commits. A bulk action records one row per selected record, so each record's History shows it.

The diff holds the changed fields only: every readable field of a new or deleted record, and the fields an update or action changed. A `sensitive` field, and a column the adapter reports as sensitive, never reaches the table. When the admin cannot read the row back after an action, the event is still recorded, without a diff.

If the table cannot be written, the error is logged and the user's change stands.

The actor is `auth.userId` of the session, and their name or email comes from `theme.user`, so the log reads "Ann Lee" rather than an ID. The request's IP and user agent are kept too.

## History on a record

Each record of an audited resource gets a History tab beside its other tabs, newest event first, twenty to a page. Each event shows the action, who and when, and each changed field as `old → new`, formatted the way the list formats that column. A reference shows the record it points at by its `labelField`, when the reader may read that record, else its id.

A long value, such as a 1 MB text edit or a large JSON object, shows its first 400 characters with **Show full value**, which loads the rest in place. One event sends at most 2,000 characters of such previews, so a page of events stays small whatever was stored. The table keeps every value whole in `diff` and a bounded copy in `diff_preview`; History and the Audit log read only the copy. Each value keeps its first 400 characters and one event keeps 4,000 in all, so a page of large edits stays small. An event recorded before 0.4 whose diff was too large to copy shows "Changes too large to preview" above each field the reader may see, and each field's **Show full value** loads it; with no such field it shows "No readable changes". The full value comes from `GET <paths.api>/audit/<event id>/value?field=<field>&side=before|after`, which answers `{ ok: true, value }` with a string as stored and an object as indented JSON, under the same rules as the page: a field, an event or a side the reader may not see answers 404.

A reader sees only the fields their `fieldAccess` lets them read. Hide the tab for one resource with `detail.history`, or stop auditing it with `audit: false`:

```ts
resource(userVisit, {
  audit: false,
});

resource(orders, {
  detail: { history: false },
});
```

## The Audit log page

The admin's navigation gets an **Audit log** entry at `/admin/audit-log`. It lists events fifty to a page, filtered by who, resource, action and date, and each event links to its record, named by its `detail.title`, else its `name`, `title` or `email`, else its id. A reader sees the events of resources their `access.read` admits and the runs of dashboard actions they may run (recorded with `resource: "dashboard"` and the action `dashboard.action.<encoded path>.<key>`), on the page and in every History tab; the Resource filter offers only those resources. An event your own route records without a `resource` shows to every reader of the page; one whose `resource` the admin does not declare shows to no one. The count stops at 10,000, and the who and action filters offer what happened in the last 90 days.

`audit.access` decides who sees the page and the History tabs. Without it, everyone `auth.access` lets in sees them. A field rule still applies to every diff.

```ts as="AdminDefinition"
audit: { enabled: true, access: ["admin"] },
```

## Tenants

With a global [`scope`](/docs/guides/multi-tenant-scope), each event stores the tenant the request was scoped to, and a reader sees only the events of their own tenant, on the page and in every History tab. The tenant is the whole scope object the request carried, so two scopes that differ in any key are two tenants (a `userId` in the scope splits a record's History by author), and a request with no scope reads only the events written without one.

A request whose scope is [`allTenants`](/docs/guides/multi-tenant-scope#staff-who-work-across-tenants) reads every tenant's events. Its own changes are filed under the tenant of the row they touch, which the resource's `scopeOf` names, so the tenant's History shows them too. A bulk action across tenants records one event per tenant.

## Your own store

A `sink` sends events to your own table or log pipeline instead. FlowPanel cannot read them back, so the admin shows no History tab and no Audit log page:

```ts as="AdminDefinition"
audit: {
  enabled: true,
  sink: async (event) => {
    console.log(JSON.stringify(event));
  },
},
```

To record an event from your own route handler, call `emitAudit(config, event)` from `@flowpanel/kit/next`; it writes wherever the admin writes. Every field: [`AuditConfig`](/docs/reference/define-config#auditconfig).
