Tenant scope has two parts: the root config resolves the tenant from the session once per request, and each tenant-owned resource turns it into a query predicate. Take the tenant from trusted session state, never from a query parameter.

## Resolve the tenant

```ts
export default defineAdmin({
  adapter,
  auth: flowpanelAuth,
  scope: async ({ session }) => {
    const tenantId = session?.user?.tenantId;
    if (!tenantId) throw new Error("No tenant selected");
    return { tenantId };
  },
  resources,
});
```

`session` is typed by the `session` you register on `FlowpanelTypes`; see [Registry](/docs/reference/registry).

The value reaches resource predicates as their first argument, and policies and actions as `ctx.scope`. Widgets get no scope: `ctx.count` and `ctx.read` apply it for you, and a `ctx.sql` or `ctx.db` query reads the tenant from `ctx.session`.

## Bind each resource

```ts
import type { QueryContext } from "@flowpanel/kit";
import { eq, type SQL } from "drizzle-orm";

resource(schema.orders, {
  columns: ["number", "status", "total", "createdAt"],
  scope: (scope, query: { where(condition: SQL): unknown }) =>
    query.where(eq(schema.orders.tenantId, scope?.tenantId as string)),
  create: {
    fields: [
      { name: "number" },
      { name: "status" },
      { name: "total" },
      {
        name: "tenantId",
        type: "hidden",
        hidden: true,
        defaultValue: async (ctx: QueryContext) => ctx.scope?.tenantId,
      },
    ],
  },
})
```

The adapter decides what `query` is, so annotate it: with Drizzle, something you call `.where(condition)` on; with Prisma, the `where` object. Merge the tenant into it:

```ts as="ResourceOptions<RowOf<'orders'>>"
scope: (scope, where: Record<string, unknown>) => ({ ...where, tenantId: scope?.tenantId }),
```

The predicate applies to lists, lookups, updates, deletes, restores, references and related tabs. On create, set the tenant with a server `defaultValue` on a hidden field, as above, so the form never shows it. A hidden field does not stop a crafted request from sending another tenant ID; the adapter does:

- On create, Drizzle checks that the new row matches the scope, and Prisma merges the scope into the data, so the write fails or lands in the caller's tenant.
- On update, both adapters refuse a change that would move the row out of the scope, through the JSON API, forms and inline edits alike. The request fails with `403` and the row stays as it was. Drizzle checks inside a transaction on PostgreSQL and MySQL and inside the `UPDATE` itself on SQLite.
- A driver without interactive transactions, such as `drizzle-orm/neon-http`, gets the same guarantee from a check that runs just before the write, as on SQLite; Prisma uses `$transaction`.

## Fail closed

With a global `scope`, every resource must declare its own `scope` or opt out with `scope: "bypass"`. A resource that does neither, or whose predicate adds no constraint, throws `FlowpanelAccessError` on its first query instead of returning another tenant's rows. Do not catch that error and retry unscoped.

`ctx.sql`, `ctx.db` and your own queries in widgets and pages are not scoped. Add the tenant predicate yourself, reading the tenant from `ctx.session`.

## Verify isolation

With fixtures for two tenants, check that:

1. each tenant lists only its own rows;
2. reading the other tenant's row by ID fails;
3. update, delete, restore and row actions cannot reach the other tenant;
4. create cannot set another tenant ID;
5. references and related tabs stay scoped;
6. dashboard queries that use `ctx.sql` or `ctx.db` filter by the tenant from `ctx.session`.
