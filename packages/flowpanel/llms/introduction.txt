# FlowPanel — Getting started

## Getting started

Add FlowPanel to an existing Next.js App Router project, expose your first Drizzle table or Prisma model, and open /admin.

Docs: https://flowpanel.tech/docs/introduction/getting-started

### Before you start

| Requirement | Supported range | Note |
| --- | --- | --- |
| Node.js | `>=20` | Required by the CLI and the kit. |
| Next.js | `>=15.5.0 <17.0.0` | App Router only. With `cacheComponents` on, 16.3 or newer. |
| React | `^19.0.0` | React DOM uses the same major version. |
| Drizzle ORM | `>=0.45.2 <1.0.0` | Required only when using the Drizzle adapter. |
| Prisma Client | `>=5.0.0 <7.0.0` | Prisma 5 and 6, only when using the Prisma adapter. Prisma 7 is not supported yet. |

Tailwind is optional: the admin stylesheet is precompiled. The Pages Router is not supported. Run every command from the project root.

### Initialize

```bash
pnpm dlx @flowpanel/cli init
```

`init` detects the package manager, ORM, app directory, path alias, database client, schema and auth helper, asks you to confirm the paths, then installs `@flowpanel/kit` and a local `@flowpanel/cli`. It stops on a conflicting file and writes nothing. `--dry-run` prints the plan without writing; `--path /ops/admin` picks the mount.

Everything the admin runs comes from `@flowpanel/kit` and its subpaths. The only other packages are the CLI and the optional [ESLint plugin](/docs/reference/eslint-plugin).

With npm, run `npx @flowpanel/cli init` and then `npx flowpanel <command>`. Yarn and bun work the same way.

### Open the config

`init` wrote `flowpanel.config.ts` at the project root. When it found no auth provider and no `getSession`, it looks like this, with your own import paths:

##### Drizzle

```ts
import { defineAdmin } from "@flowpanel/kit";
import { drizzleAdapter } from "@flowpanel/kit/drizzle";
import { db } from "@/server/lib/db";
import * as schema from "@/server/lib/db/schema";
import { getSession } from "@/server/lib/auth";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof db;
    schema: typeof schema;
    session: NonNullable<Awaited<ReturnType<typeof getSession>>>;
  }
}

export default defineAdmin({
  paths: { admin: "/admin", api: "/api/flowpanel" },
  adapter: drizzleAdapter({ db, schema }),

  auth: {
    session: getSession,
    role: (s) => s?.user.role ?? "guest",
    access: "admin",
  },

  realtime: { driver: "memory" },

  theme: {
    brand: { name: "My app" },
    mode: "auto",
  },

  resources: [
    // pnpm flowpanel new <table>  adds an entry; or write resource(schema.users, { columns: ["email", "name", "createdAt"] })
  ],
});
```

##### Prisma

```ts
import { defineAdmin } from "@flowpanel/kit";
import { prismaAdapter } from "@flowpanel/kit/prisma";
import { prisma } from "@/lib/prisma";
import { getSession } from "@/server/lib/auth";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof prisma;
    session: NonNullable<Awaited<ReturnType<typeof getSession>>>;
  }
}

export default defineAdmin({
  paths: { admin: "/admin", api: "/api/flowpanel" },
  adapter: prismaAdapter({ prisma, provider: "postgresql" }),

  auth: {
    session: getSession,
    role: (s) => s?.user.role ?? "guest",
    access: "admin",
  },

  realtime: { driver: "memory" },

  theme: {
    brand: { name: "My app" },
    mode: "auto",
  },

  resources: [
    // pnpm flowpanel new <model>  adds an entry; or write resource("User", { columns: ["email", "name", "createdAt"] })
  ],
});
```

The `declare module` block registers your database, your schema and your session type, so resource names, rows and the `s` in `auth.role` are typed. If your auth module already exports `getSession`, the config imports it and `role` is a longer guard that reads `user.role` defensively. When `init` finds better-auth, Auth.js, Clerk or Lucia, `auth` is `flowpanelAuth` from `server/lib/flowpanel-session.ts` instead, and that module registers the session.

### Connect auth

`access: "admin"` lets in only sessions whose role is `admin`, so the admin needs your session.

- With a detected provider, `server/lib/flowpanel-session.ts` holds the matching preset, which reads the role from `session.user.role`. Make sure your user's session carries the `admin` role.
- With your own `getSession`, the config uses it as it is.
- Otherwise `server/lib/auth.ts` exports a `getSession` that returns `null`, so every request is denied. Return your session from it, or run `pnpm flowpanel init --dev-auth` for a development identity that refuses to run in production.

The stub `init` wrote in that last case, which denies every request:

```ts
// Return the signed-in session here, e.g. auth.api.getSession({ headers: await headers() }); until then the admin rejects every request.
type Session = { user: { id: string; role: string } };

export async function getSession(): Promise<Session | null> {
  return null;
}
```

[Authentication](/docs/guides/authentication) covers each provider and how the role is read.

### Add your first resource

`pnpm flowpanel new <table>` (the model name with Prisma) writes a resource entry for you; see [flowpanel new](/docs/reference/cli#flowpanel-new). To write it yourself, open `flowpanel.config.ts`, add `resource` to the `@flowpanel/kit` import and put this entry in `resources`:

##### Drizzle

```ts
resources: [
  resource(schema.users, {
    columns: ["email", "name", "role", "createdAt"],
    search: ["email", "name"],
    defaultSort: { field: "createdAt", dir: "desc" },
  }),
],
```
Drizzle infers the row type from the table, so a misspelt column fails the type check.

##### Prisma

```ts
resources: [
  resource("User", {
    name: "users",
    columns: ["email", "name", "role", "createdAt"],
    search: ["email", "name"],
    defaultSort: { field: "createdAt", dir: "desc" },
  }),
],
```
A Prisma resource is a model name, so bind it to the generated type: add `interface FlowpanelResources { users: import("@prisma/client").User }` inside the `declare module "@flowpanel/kit"` block. The columns are then checked against the model. `flowpanel new` does this for you.

### Start the admin

```bash
pnpm dev
```

Open [http://localhost:3000/admin](http://localhost:3000/admin). The resource is in the navigation. A sign-in screen means the request had no session with the `admin` role; see [Connect auth](#connect-auth).

`pnpm flowpanel dev` runs Next.js too, and also starts the [queue board](/docs/guides/queues) when `REDIS_URL` is set and `scripts/board-server.mts` exists. Only the board needs `tsx` (`pnpm add -D tsx`).

### What `init` created

Paths start with `src/` in a `src/app` project.

| File | Purpose |
| --- | --- |
| `flowpanel.config.ts` | Resources, dashboards, auth, scope, realtime and theme |
| `server/lib/flowpanel-session.ts` | With a detected auth provider: its preset, your session and role |
| `server/lib/auth.ts` | With no provider and no `getSession`: a stub that denies every request |
| `app/admin/[[...slug]]/page.tsx` | Catch-all admin page; exports `generateMetadata` |
| `app/admin/layout.tsx` | Imports the stylesheet and the theme script |
| `app/admin/not-found.tsx` | 404 page inside the admin chrome |
| `app/api/flowpanel/[...route]/route.ts` | Resource and action handlers |
| `app/api/flowpanel/stream/route.ts` | Authenticated SSE endpoint |
| `styles/admin.css` | One import of the precompiled, isolated stylesheet |
| `flowpanel/migrations/0001_init.sql` | SQL for `_flowpanel_migrations` and `flowpanel_audit_log` |

`init` also adds `suppressHydrationWarning` to the root layout's `<html>` tag, because `ThemeScript` sets an attribute on it before hydration. If it cannot patch the file safely, it prints the edit. `flowpanel doctor --fix` restores a missing route file.

### Optional: the audit log

```bash
pnpm flowpanel migrate
```

Run this before you turn on the audit log with `audit: { enabled: true }`; skip it otherwise. The command applies `flowpanel/migrations` through the database client in `flowpanel.config.ts` and creates `_flowpanel_migrations` and `flowpanel_audit_log`, the table behind each record's History tab and the Audit log page. `init` writes the SQL for your database: PostgreSQL, MySQL or SQLite. See [Audit log](/docs/guides/audit-log).

## Build a complete admin

From an empty Next.js app to a deployed admin with dashboards, a record page, a custom widget, live updates and a smoke test.

Docs: https://flowpanel.tech/docs/introduction/founder-admin

This tutorial builds the admin a founder opens every morning, using the domain of the [ScrapeAI example](https://github.com/getflowpanel/flowpanel/tree/main/examples/ai-scraper): customers set up monitors, monitors produce runs, and runs find listings on marketplaces. It assumes a Next.js 16 app created by `create-next-app` with a `src/` directory, a Drizzle schema and better-auth. Imports use that app's default alias, `@/*` for `./src/*`, so `@/db/schema` is `src/db/schema.ts`. Each step ends with what you should see.

### 1. Install

```bash
pnpm dlx @flowpanel/cli init
pnpm dev
```

You should see a sign-in screen at `/admin`. Sign in as a user whose `role` is `"admin"` (better-auth's admin plugin, or a `role` additional field), and `/admin` shows an empty navigation.

### 2. Types from your schema and your auth

`init` wrote `flowpanel.config.ts`, which registers your database and schema:

```ts
import { defineAdmin } from "@flowpanel/kit";
import { drizzleAdapter } from "@flowpanel/kit/drizzle";
import { db } from "@/db";
import * as schema from "@/db/schema";
import { flowpanelAuth } from "@/server/lib/flowpanel-session";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof db;
    schema: typeof schema;
  }
}

export default defineAdmin({
  paths: { admin: "/admin", api: "/api/flowpanel" },
  adapter: drizzleAdapter({ db, schema }),

  auth: flowpanelAuth,

  realtime: { driver: "memory" },

  theme: {
    brand: { name: "scrapeai" },
    mode: "auto",
  },

  resources: [
    // pnpm flowpanel new <table>  adds an entry; or write resource(schema.users, { columns: ["email", "name", "createdAt"] })
  ],
});
```

Your auth module exports a better-auth instance and no `getSession`, so `init` also wrote `src/server/lib/flowpanel-session.ts`, which registers the session and wraps the instance in the better-auth preset:

```ts
// Session module for better-auth; flowpanel.config.ts takes its auth block from flowpanelAuth.
import { withBetterAuth } from "@flowpanel/kit/auth";
import { auth } from "@/lib/auth";

export const flowpanelAuth = withBetterAuth({
  auth,
  access: "admin",
  // role: async (session) => (await findMember(session?.user?.id))?.role ?? "guest",
});

export const getSession = flowpanelAuth.session;

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    session: typeof auth.$Infer.Session;
  }
}
```

The config takes its `auth` from `flowpanelAuth`. The preset reads the role from `session.user.role` and the audit actor from `session.user.id`. Every resource name, row and `ctx.session` is typed.

You should see a type error if you put `resource(schema.nope, {})` in `resources`, because your schema has no `nope` table. Remove it again.

### 3. One resource per file

Move the config into `src/admin/config/index.ts` and leave a re-export at the root, so the admin route and the CLI still find it:

```bash
mkdir -p src/admin/config
mv flowpanel.config.ts src/admin/config/index.ts
echo 'export { default } from "./src/admin/config";' > flowpanel.config.ts
```

Fix any relative imports in the moved file. Then write one file per table, starting with the tables others point at:

```bash
pnpm flowpanel new customers --dir src/admin/config/resources
pnpm flowpanel new monitors --dir src/admin/config/resources
pnpm flowpanel new runs --dir src/admin/config/resources
pnpm flowpanel new invoices --dir src/admin/config/resources --hidden
```

Each command reads the table, picks columns by type, and adds the export to `src/admin/config/resources/index.ts`. A foreign key becomes a `reference` labelled by the target's `name`, `title` or `email`, and a picker in the create and edit form, once the target has its own file, which is why `customers` goes first. `--hidden` keeps invoices out of the navigation; they appear on the customer's page.

The first `new --dir` wired the directory into the config, so `src/admin/config/index.ts` now reads:

```ts
import { defineAdmin } from "@flowpanel/kit";
import { drizzleAdapter } from "@flowpanel/kit/drizzle";
import { db } from "@/db";
import * as schema from "@/db/schema";
import { flowpanelAuth } from "@/server/lib/flowpanel-session";
import { resources } from "@/admin/config/resources";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof db;
    schema: typeof schema;
  }
}

export default defineAdmin({
  paths: { admin: "/admin", api: "/api/flowpanel" },
  adapter: drizzleAdapter({ db, schema }),

  auth: flowpanelAuth,

  realtime: { driver: "memory" },

  theme: {
    brand: { name: "scrapeai" },
    mode: "auto",
  },

  resources: [...resources],
});
```

You should see Customers, Monitors and Runs in the navigation, and every run naming its monitor.

### 4. Declare each enum once

```ts
// src/admin/config/enums.ts
import { enumOf } from "@flowpanel/kit";
import { accountStatus, planTier, runStatus } from "@/db/schema";

export const RunStatus = enumOf(runStatus.enumValues, {
  queued: ["Queued", "muted"],
  running: ["Running", "info"],
  success: ["Success", "ok"],
  failed: ["Failed", "err"],
});

export const Plan = enumOf(planTier.enumValues, {
  free: ["Free", "muted"],
  starter: ["Starter", "info"],
  pro: ["Pro", "accent"],
  business: ["Business", "accent"],
});

export const AccountStatus = enumOf(accountStatus.enumValues, {
  active: ["Active", "ok"],
  trialing: ["Trialing", "info"],
  past_due: ["Past due", "err"],
  canceled: ["Canceled", "muted"],
});

export const Site = enumOf({
  amazon: "Amazon",
  best_buy: "Best Buy",
  ebay: "eBay",
  newegg: "Newegg",
  walmart: "Walmart",
  media_markt: "MediaMarkt",
  mercado_libre: "Mercado Libre",
});
```

For a database enum, a value missing from the map is a compile error. `listings.site` is a text column, so `Site` lists its values itself. Replace the `enumOf` stub `flowpanel new` wrote in each resource file with the shared enum. The runs file becomes:

```ts
// src/admin/config/resources/runs.ts
import { resource } from "@flowpanel/kit";
import * as schema from "@/db/schema";
import { RunStatus } from "../enums";

export const runs = resource(schema.runs, {
  columns: [
    "id",
    { field: "monitorId", label: "Monitor", reference: { resource: "monitors", labelField: "name" } },
    { field: "status", format: RunStatus.format },
    "pagesCrawled",
    "durationMs",
    { field: "startedAt", format: { kind: "date", time: true } },
    { field: "finishedAt", format: { kind: "date", time: true } },
    "error",
  ],
  filters: [{ field: "status", type: "multiselect" }],
  defaultSort: { field: "startedAt", dir: "desc" },
});
```

Do the same with `Plan` and `AccountStatus` in `customers.ts`. A select filter on an enum-formatted column lists the enum's labels, so it needs no `options`.

You should see coloured status badges and a status filter with four labels.

### 5. A dashboard

Every widget receives `ctx`. Pick the call by what you need:

| You want | Use | Scope, access, soft delete applied |
|---|---|---|
| how many rows | `ctx.count(resource, where, { range })` | yes |
| the rows | `ctx.read(resource, { where, range })` | yes |
| the record on this card | `ctx.rowOf(resource)` | yes |
| a number only SQL can define | ``ctx.sql`…` `` | no, add the predicates |
| your ORM | `ctx.db` | no |
| one result for several widgets | `ctx.query(fn)` around any of the above | n/a |

Start with a strip of numbers compared with the period before:

```ts
// src/admin/config/dashboards/overview.ts
import { dashboard, metric } from "@flowpanel/kit";

export const overview = dashboard({
  path: "/",
  label: "Overview",
  dateRange: { preset: "today", presets: ["today", "yesterday", "last7d", "last30d"] },
  refresh: "60s",
  sections: [
    {
      variant: "strip",
      widgets: [
        metric("Runs", { count: "runs", range: "startedAt" }, { compare: true }),
        metric(
          "Failed runs",
          { count: "runs", where: { status: "failed" }, range: "startedAt" },
          { compare: true, goodWhen: "down" },
        ),
        metric("New customers", { count: "customers", range: "createdAt" }, { compare: true }),
      ],
    },
  ],
});
```

Import `overview` into `src/admin/config/index.ts` and add `dashboards: [overview]` to `defineAdmin`. Each number links to the rows it counted, for the same period, through a `daterange` filter on the counted date. Give each resource one; in `runs.ts`:

```ts
filters: [
  { field: "status", type: "multiselect" },
  { field: "startedAt", type: "daterange" },
],
```

Do the same for `createdAt` on customers and `paidAt` on invoices. `defineAdmin` names a missing one.

You should see three numbers in one band, each with its change and a link to its rows.

### 6. One SQL statement, several widgets

Write the statement once and let FlowPanel bucket and rank it:

```ts
// src/admin/config/dashboards/marketplaces.ts
import { bars, breakdown, dashboard, lineChart, series, type WidgetContext } from "@flowpanel/kit";
import { Site } from "../enums";

export const listingsFound = (c: WidgetContext) =>
  c.sql<{ at: Date; site: string }>`
    select l.scraped_at as at, l.site
    from listings l
    where l.scraped_at >= ${c.dateRange.from} and l.scraped_at < ${c.dateRange.to}
      and (${c.filters.site ?? null}::text is null or l.site = ${c.filters.site ?? null})`;

const marketplace = { key: "site", label: "Marketplace", options: Site };

export const marketplaces = dashboard({
  path: "/marketplaces",
  label: "Marketplaces",
  dateRange: { preset: "last7d", presets: ["today", "last7d", "last30d"] },
  filters: [marketplace],
  sections: [
    {
      widgets: [
        bars({
          label: "Listings by marketplace",
          query: async (c) => breakdown(await c.query(listingsFound), { by: "site", labels: Site }),
          share: true,
          compare: true,
          filterOnClick: "site",
          span: 4,
        }),
        lineChart(
          "Listings per day",
          async (c) =>
            series(await c.query(listingsFound), c.dateRange, { at: "at", by: "site", grain: "day" }),
          { x: "date", labels: Site, span: 8 },
        ),
      ],
    },
  ],
});
```

Import `marketplaces` into the config and add it to `dashboards`. `c.query(listingsFound)` runs the statement once per request, plus once for the previous period `compare` asks for. `series` buckets rows by day in the admin's time zone and fills gaps; `breakdown` ranks them with shares. `ctx.sql` applies no scope, so a multi-tenant admin adds its tenant predicate to the statement.

You should see bars with shares and changes, and a line per marketplace. Clicking a bar narrows the whole page to that marketplace.

### 7. Status at a glance

A tracker shows one row per marketplace and one block per hour. Put it in its own file:

```ts
// src/admin/config/dashboards/listings-by-hour.ts
import { type Threshold, tracker } from "@flowpanel/kit";
import { Site } from "../enums";
import { listingsFound } from "./marketplaces";

const QUIET: Threshold = { warn: 5, err: 1 };

export const listingsByHour = tracker({
  label: "Listings found · 24 h",
  query: listingsFound,
  at: "at",
  by: "site",
  keys: Site.values,
  labels: Site,
  tones: QUIET,
  filterOnClick: "site",
  span: 12,
});
```

In `marketplaces.ts`, add `listingsByHour` to the first section's `widgets` after the line chart. The tracker always shows the last 24 hours. `keys: Site.values` keeps a marketplace on the board when it found nothing. `warn` above `err` means fewer is worse: 5 listings or fewer is a warning, 1 is an error, and an hour with none stays grey.

You should see 24 hourly blocks per marketplace, coloured by how many listings each hour found.

### 8. A record page

```ts
// src/admin/config/resources/customer-card.ts
import {
  checklist,
  type DetailOptions,
  enumOf,
  filled,
  kv,
  metric,
  related,
  type RowOf,
  timeline,
} from "@flowpanel/kit";
import { AccountStatus, Plan } from "../enums";

const Activity = enumOf({
  monitor: ["Monitor added", "info"],
  paid: ["Invoice paid", "ok"],
});

export const paidInvoices = metric(
  "Paid invoices",
  { count: "invoices", where: { status: "paid" }, range: "paidAt" },
  { compare: true },
);

export const customerCard = {
  title: (c) => c.company ?? c.email,
  subtitle: (c, { format }) => `Customer since ${format.date(c.createdAt)}`,
  badge: (c) => [
    AccountStatus.badge(c.status, { href: { resource: "customers", filter: { status: c.status } } }),
    Plan.badge(c.plan),
  ],
  dateRange: { preset: "last30d", presets: ["last7d", "last30d", "QTD"] },
  stats: [metric("Monitors", { count: "monitors" }), paidInvoices],
  aside: [
    kv({
      label: "Account",
      columns: 1,
      items: [
        { label: "Email", field: "email" },
        { label: "Plan", field: "plan", format: Plan.format },
        { label: "Last seen", field: "lastSeenAt", format: "relative" },
      ],
    }),
    checklist({
      label: "Profile",
      items: async (c) => filled(c.rowOf("customers"), { name: "Name", company: "Company" }),
    }),
  ],
  tabs: [
    {
      key: "activity",
      label: "Activity",
      widgets: [
        timeline({
          kinds: Activity,
          sources: [
            timeline.source("monitors", { kind: "monitor", at: "createdAt", title: (m) => m.name }),
            timeline.source("invoices", {
              kind: "paid",
              at: "paidAt",
              title: (i, _refs, c) => c.format.money(i.amountCents, { scale: 100 }),
            }),
          ],
        }),
      ],
    },
    related("monitors"),
    related("invoices", { sort: { field: "createdAt", dir: "desc" } }),
  ],
} satisfies DetailOptions<RowOf<"customers">>;
```

Pass it as `detail: customerCard` on the customers resource. The strip and the side column stay on every tab. The related tabs find their filter from the `customerId` reference and show row counts in their labels. `paidInvoices` is exported so a unit test can import it (step 11).

You should see status and plan badges, the monitor count, the invoices paid in the picked period, account facts beside the tabs, and an activity feed grouped by day. See [Record pages and drawers](/docs/build/detail-cards).

### 9. A custom widget

A widget no built-in card fits is a server component built from kit atoms:

```tsx
// src/admin/ui/CrawlQueue.tsx
import { type Tone, toneTextClass } from "@flowpanel/kit";
import { StatusDot } from "@flowpanel/kit/react";

export function CrawlQueue({ waiting, failed }: { waiting: number; failed: number }) {
  const tone: Tone = failed > 0 ? "err" : waiting > 100 ? "warn" : "ok";
  return (
    <p className="flex items-center gap-2 text-sm">
      <StatusDot tone={tone} />
      <span className={toneTextClass[tone]}>
        {waiting} waiting · {failed} failed
      </span>
    </p>
  );
}
```

`custom()` places it in a section. `queueCounts` is your own function in `src/server/lib/queue.ts` returning `{ waiting, failed }`:

```ts
// src/admin/config/dashboards/crawl-queue.ts
import { custom } from "@flowpanel/kit";
import { queueCounts } from "@/server/lib/queue";
import { CrawlQueue } from "../../ui/CrawlQueue";

export const crawlQueue = custom(CrawlQueue, (c) => c.query(queueCounts), {
  label: "Crawl queue",
  realtime: "pipeline",
  span: 4,
});
```

In `overview.ts`, import `crawlQueue` and add `{ widgets: [crawlQueue] }` to `sections`.

You should see a "Crawl queue" card that matches its neighbours. See [Build a custom widget](/docs/customization/custom-widgets).

### 10. Live updates from the worker

Install `ioredis` with `pnpm add ioredis`. Keep the realtime options in one module that the admin config and the worker both import:

```ts
// src/shared/realtime.ts
import type { PublisherOptions } from "@flowpanel/kit";

export const realtime = {
  driver: "redis",
  url: process.env.REDIS_URL!,
  keyPrefix: `scrapeai-${process.env.NODE_ENV}`,
} satisfies PublisherOptions;
```

Pass it to `defineAdmin` with the channel the crawl-queue card subscribes to, `realtime: { ...realtime, channels: { pipeline: {} } }`. Then publish from the worker:

```ts
// src/worker/admin-events.ts
import { createPublisher } from "@flowpanel/kit/publish";
import { realtime } from "@/shared/realtime";

export const adminEvents = createPublisher(realtime);

/** Call it when the crawler saves a run. */
export async function runSaved(run: { id: number }): Promise<void> {
  await adminEvents.resource("runs", { id: run.id });
  await adminEvents.publish("pipeline");
}
```

A Redis error never fails the crawl. Subscribe the runs list to those events in `runs.ts`:

```ts
realtime: true,
```

`realtime: true` on the runs resource refreshes its list, and the crawl queue card listens on `"pipeline"`. With both dashboards and the shared realtime options, the config reads:


You should see the runs list and the crawl queue card update during a crawl, without a reload. See [Realtime](/docs/guides/realtime#publish-from-a-worker).

## Why FlowPanel

Decide whether an embedded, schema-aware admin fits your application better than a hosted tool, an admin framework or a database browser.

Docs: https://flowpanel.tech/docs/introduction/why-flowpanel

FlowPanel is for a team with a Next.js App Router app on Drizzle or Prisma that needs an internal admin: lists, forms, actions, dashboards, imports, queues and live updates. You name the tables and fields in a typed config; only those appear.

### What stays in your application

The admin is pages and route handlers in your Next.js app. Your repository holds the config, your database client runs the queries, your auth provider creates the session, and your deployment serves it. No third party receives your database credentials or rows.

Authorization, tenant scope, migrations, monitoring and scaling the realtime publisher stay your responsibility. [Production readiness](/docs/guides/production-readiness) lists them.

### How it compares

- **Prisma Studio, Drizzle Studio** show every table to a developer. FlowPanel shows the resources and fields you name to operators, behind your auth and role checks.
- **react-admin, Refine** are React frameworks: you write a data provider and the pages. FlowPanel queries through your ORM client and generates the pages from config.
- **AdminJS** mounts a separate admin on Express, Fastify or Nest. FlowPanel runs inside the Next.js app you already deploy.
- **Retool** and other hosted builders are edited in a browser and connect to your database from their side. A FlowPanel config goes through code review with the rest of your app.

### When to choose something else

Choose another tool if you need a hosted no-code admin, a frontend outside Next.js, the Pages Router, REST or GraphQL data providers, or a database neither Drizzle nor Prisma supports and you do not want to write an adapter.

Before you commit, read [What FlowPanel does not do yet](/docs/introduction/limits). Next: [Getting started](/docs/introduction/getting-started).

## What FlowPanel does not do yet

The gaps in 0.4 that a real admin runs into, and the workaround for each.

Docs: https://flowpanel.tech/docs/introduction/limits

FlowPanel 0.4 covers lists, forms, actions, dashboards, record pages, imports, queues and live updates. These are the gaps you will meet first, with the way to work around each one today.

### File uploads

No form field accepts a file. Upload the file in your own code and store its URL in a text column; the list shows it with the `url` [column format](/docs/reference/resources#columnformat). For the upload control itself, [eject the resource](/docs/customization/eject) (`flowpanel eject resource <name>`) and build the upload into its create and edit pages, or add a [`page()`](/docs/reference/widgets#pageconfig) with your own upload form.

### Editing many-to-many links

A form writes the columns of one table, so it cannot add or remove rows of a join table. Add a [row action](/docs/build/actions) whose form has a `multiselect` field listing the other side, and replace the join rows in its `run`. A `related()` tab on the [record page](/docs/build/detail-cards#related-rows) shows the linked rows.

### Signing in as a user

The admin has no "sign in as" button. Your auth provider decides how impersonation works, so call it from a [row action](/docs/build/actions): better-auth's admin plugin, for example, creates an impersonation session for a user id, and the action returns `redirect` with the path to open as that user.

### Prisma 7

The Prisma adapter supports Prisma 5 and 6. Prisma 7's generated client no longer carries the field metadata the adapter reads, so `init` and `doctor` stop on it. Stay on Prisma 6, or use the [Drizzle adapter](/docs/introduction/drizzle); [Prisma 7](/docs/introduction/prisma#prisma-7) has the details.

### Not-found status under cacheComponents

With `cacheComponents` on, an unknown admin URL shows the not-found screen with status 200, because Next.js has already streamed the page shell when the admin finds that the record is missing. The page is `noindex`, so search engines skip it; an uptime check that relies on the status should look for the "Page not found" title instead. See [`createFlowpanel`](/docs/reference/next-runtime#createflowpanel).

## Drizzle setup

Connect FlowPanel to an existing Drizzle ORM project on PostgreSQL, MySQL or SQLite.

Docs: https://flowpanel.tech/docs/introduction/drizzle

The Drizzle adapter reads row types and columns from your schema and runs queries through your `db` client. Import it from `@flowpanel/kit/drizzle`. PostgreSQL, MySQL and SQLite are supported; version ranges are in [Getting started](/docs/introduction/getting-started#before-you-start).

### Configure the adapter

```ts
import { defineAdmin, resource } from "@flowpanel/kit";
import { drizzleAdapter } from "@flowpanel/kit/drizzle";
import { getSession } from "@/server/lib/auth";
import { db } from "@/server/lib/db";
import * as schema from "@/server/lib/db/schema";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof db;
    // Every table and view in the schema becomes a typed resource name and row.
    schema: typeof schema;
    session: NonNullable<Awaited<ReturnType<typeof getSession>>>;
  }
}

export default defineAdmin({
  adapter: drizzleAdapter({ db, schema }),
  auth: {
    session: getSession,
    role: (s) => s?.user.role ?? "guest",
    access: "admin",
  },
  resources: [
    resource(schema.users, {
      columns: ["email", "name", "role", "createdAt"],
      search: ["email", "name"],
      defaultSort: { field: "createdAt", dir: "desc" },
    }),
  ],
});
```

Pass the `db` and schema namespace your app already uses. The dialect is inferred from a table in `schema`; set `dialect` only when the schema has no Drizzle table. With `schema` registered in `FlowpanelTypes`, every table and view is a typed resource name and row.

Search and filters are dialect-aware, pagination is offset-based, and a configured soft-delete field is set instead of deleting the row.

### Views

A resource can read a SQL view, so the list sorts and filters by numbers the view computes per row. Declare the view with `.existing()` so drizzle-kit leaves it alone, and create it in your own migration:

```ts
import { integer, pgView, text } from "drizzle-orm/pg-core";

export const adminUserRow = pgView("admin_user_row", {
  id: text("id").primaryKey(),
  name: text("name"),
  sent30d: integer("sent_30d"),
}).existing();
```

```sql
create view admin_user_row as
select u.id, u.name,
  (select count(*) from response r
    where r.user_id = u.id and r.sent_at > now() - interval '30 days')::int as sent_30d
from "user" u;
```

Write each per-row number as a correlated subquery rather than a `group by` over the table: reading one record stays an index lookup, and sorting computes the number only for the page's rows.

`resource(adminUserRow, { name: "user", writeTo: user })` reads the view and writes edits to `user`. Without `writeTo` the resource is read-only. See [Reading a view](/docs/reference/resources#reading-a-view).

### Limitation

Relations declared with `relations()` do not become joined list columns. Use a [reference field](/docs/build/forms#relation-fields), a [column renderer](/docs/customization/column-renderers) or a view.

## Prisma setup

Connect FlowPanel to an existing Prisma project on PostgreSQL, MySQL or SQLite.

Docs: https://flowpanel.tech/docs/introduction/prisma

The Prisma adapter reads model metadata from DMMF and runs queries through your Prisma Client. Import it from `@flowpanel/kit/prisma` and run `prisma generate` first. It supports Prisma 5 and 6; [Prisma 7](#prisma-7) is not supported yet. Version ranges are in [Getting started](/docs/introduction/getting-started#before-you-start).

### Prisma 7

Prisma 7's generated client no longer carries the field metadata in `Prisma.dmmf` (ids, nullability, defaults) that the adapter reads to build columns and forms.

On Prisma 7, `init` and `doctor` stop with `@prisma/client is unsupported`, followed by the version they found and the supported range, `>=5.0.0 <7.0.0`. A hand-written config fails when the admin loads, with `prismaAdapter: Prisma.dmmf has no field metadata`.

Stay on Prisma 6, keep the `prisma-client-js` generator in `schema.prisma`, and generate the client again:

```bash
pnpm add @prisma/client@6
pnpm add -D prisma@6
pnpm prisma generate
```

If the project has to stay on Prisma 7, use the [Drizzle adapter](/docs/introduction/drizzle) or a [custom adapter](/docs/understand/adapters#custom-adapters).

### Configure the adapter

```ts
import { defineAdmin, resource } from "@flowpanel/kit";
import { prismaAdapter } from "@flowpanel/kit/prisma";
import { getSession } from "@/server/lib/auth";
import { prisma, type User } from "@/server/lib/prisma";

declare module "@flowpanel/kit" {
  interface FlowpanelTypes {
    db: typeof prisma;
    session: NonNullable<Awaited<ReturnType<typeof getSession>>>;
  }
  interface FlowpanelResources {
    users: User;
  }
}

export default defineAdmin({
  adapter: prismaAdapter({ prisma, provider: "postgresql" }),
  auth: {
    session: getSession,
    role: (s) => s?.user.role ?? "guest",
    access: "admin",
  },
  resources: [
    resource("User", {
      name: "users",
      columns: ["email", "name", "role", "createdAt"],
      search: ["email", "name"],
      defaultSort: { field: "createdAt", dir: "desc" },
    }),
  ],
});
```

`provider` is the `datasource` provider from `schema.prisma`: `"postgresql"`, `"mysql"` or `"sqlite"`. It is required because `flowpanel migrate` locks and splits SQL differently for each.

Use the PascalCase model name, `"User"`, not the delegate `"user"`. Without `name`, the model name is the URL slug and the navigation label; `flowpanel new` sets `name: "users"` from `@@map` or the plural of the model. A model name is a string, so add its row to `FlowpanelResources` under the resource name to type it.

Columns with `@default(...)` or `@updatedAt` are optional in the create form, and Prisma or the database fills them. A `Decimal` comes back as a string at its `@db.Decimal` scale, so `49.90` reads `"49.90"`. Prisma 5 does not report the scale, so there it reads `"49.9"`.

Pagination is offset-based and integer primary keys are coerced from the URL. Search uses Prisma's `contains`; the provider and collation decide case sensitivity. Soft delete works with a nullable field such as `deletedAt`.

### Views

A Prisma `view` model reads like any model. The adapter does not report it as a view, so FlowPanel cannot make it read-only: set [`writeTo`](/docs/reference/resources#reading-a-view) to the model that holds the rows, or disable `create`, `update` and `delete`.

### Limitation

Relations, JSON sub-fields and computed values are not list columns. Use a [column renderer](/docs/customization/column-renderers), a view, or a custom adapter.
